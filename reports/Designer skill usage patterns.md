# Naming skills sidesteps most library bloat

Nobody has measured how many skills a typical product designer or Claude Code power user installs, but every available signal says the sets people actually use are small. Designers who describe their real setups run single digits, mostly skills they built themselves. Power users who post "what I actually use" land on 8 to 10. The big numbers (42, 63, 86, 380+) are pack sizes offered by their authors, and the only hard counts of large installs come from GitHub bug reports filed by people whose libraries broke. A setup of about 300 skills sits at the far end of even that self-selected group. The way you invoke them is the normal part: designers who describe real work call skills by name or slash command, partly because automatic triggering is unreliable. Anthropic's docs describe two costs of a large library. Every listed description competes for attention, which lowers selection accuracy. Past a fixed budget of 1% of the context window, Claude Code deletes descriptions outright, starting with the least used skills. Both costs land on automatic triggering. Skill names are never dropped, so calling a skill by name keeps working at any count. The real risks for a 300 skill, name-driven setup are narrower: a fixed per-turn context cost, overlapping skills that contradict each other when stacked and a few settings that would quietly break name invocation if you used them to trim the library.

## No survey exists, and the counts that do exist describe supply

The evidence base is thin, and its shape matters. No survey measures designers' skill counts, sources or triggering habits. The closest survey figures are general: Figma's 2026 State of the Designer reportedly found 72% of designers use generative AI, but that number reaches us secondhand through a Korean blog, not the primary report ([braindetox](https://braindetox.kr/en/posts/claude_designer_ai_build_2026.html)). A JetBrains survey of more than 10,000 developers found **18% use Claude Code at work**, which says nothing about skills ([claudify](https://claudify.tech/blog/state-of-claude-code-2026)).

What exists instead falls into three kinds of evidence, and they should not be blended.

| Kind | What it shows | Example |
|---|---|---|
| Measured counts | Real installed totals, but only from people who hit a bug | GitHub issues reporting 30 to 290 skills |
| Install counters | Total CLI installs across all users, mostly engineers | skills.sh: `frontend-design` at 887.9K |
| Anecdote | One person's account of their own setup | Designers describing 1 to 7 skills |

**Measured counts from bug reports.** The reporter of issue #81081 had 36 project skills plus about 30 personal ones. Commenters reported 50, 77 and finally one user who grew from 189 to 290 SKILL.md files. That last user had **usage records for only 44 of 255 skills** ([Issue #81081](https://github.com/anthropics/claude-code/issues/81081)). This is the single strongest data point on the gap between installed and used. These people found the issue tracker because their libraries overflowed the budget, so they mark the high end, not the middle.

**Install counters.** As of a 15 September 2026 snapshot, skills.sh showed `frontend-design` at **887.9K installs**, `web-design-guidelines` at 635.2K and `impeccable` at 277.2K ([Critique](https://www.critique.sh/blog/best-ui-skills-for-ai-agents)). Snapshots conflict across sites. Installing a pack counts every skill in it, and nothing splits the figures by role. They show that design skills are popular. They do not show that designers install big packs.

**Anecdote from designers.** Clinton Halpin, a designer on an AI design team, describes three items: two skills he built (`/prototype-loop` and `/setup`) and one he installed (`/ralph-loop`) ([Clinton Halpin](https://clintonhalpin.com/blog/using-claude-code-for-product-design/)). Isaac Sanchez, a freelance design engineer, describes one skill he built plus two installed ones. His method is to do the work with Claude first, then have Claude write the skill from what worked ([uxisaac.com](https://www.uxisaac.com/blog/claude-code-skills-ux-design-workflow)). A French UX designer describes a seven skill set from discovery to handoff ([uxbrady](https://uxbrady.medium.com/claude-skills-pour-les-ux-designers-18672f4a9599)). Felix Lee's ADPList guide for designers mentions no skills at all ([ADPList](https://adplist.substack.com/p/claude-code-guide-for-designers)), which suggests plenty of designers never get past plain prompts.

The large numbers in designer discourse come from people distributing skills. MC Dean published a free collection of **63 skills and 27 commands** in 8 plugins and tells readers to install whichever plugins they want ([MC Dean](https://marieclairedean.substack.com/p/i-built-63-design-skills-for-claude)). Tridip Thrizu sells a 42 skill pack for $99 and tells buyers to start with one skill, `/audit-ux` ([solodesign.cc](https://solodesign.cc/blog/claude-code-for-designers/)). RefoundAI's "Lenny Skills" pack is listed at 76 or 86 skills depending on the page ([GitHub](https://github.com/refoundai/lenny-skills)). Bundles outside design go further, with one repo shipping **380+ skills in a single install** ([alirezarezvani/claude-skills](https://github.com/alirezarezvani/claude-skills)). Pack authors and course sellers have an incentive to present big collections. Their counts describe supply. Even they tell buyers to start with one.

## Practitioner advice converges on curating a few that do not overlap

The advice is consistent across neutral guides, Reddit and vendor docs, though all of it is opinion rather than measurement. Critique recommends picking one direction skill, one implementation skill and one audit skill, and warns that `frontend-design`, `design-taste-frontend`, `ui-ux-pro-max` and `impeccable` will **"fight each other"** when they run together ([Critique](https://www.critique.sh/blog/best-ui-skills-for-ai-agents)). Hashin Panakkaparambil recommends installing only what each task needs and warns that overlapping skills produce contradictory rules ([hashp](https://hashp.substack.com/p/claude-code-design-skills-a-guided)). A March 2026 r/ClaudeAI thread on whether Claude Code can have too many skills settled on dozens being fine only when well differentiated, with one commenter putting it as "Skills should be scars, not a junk drawer" ([Reddit snapshot](https://reddit.sentinel-team.org/posts/1uhzgtm/snapshots/2026-07-03T03%3A00%3A16.73148Z)). Figma tells teams to keep each skill to one workflow and not to build skills for one-off tasks ([Figma](https://www.figma.com/resource-library/how-to-create-a-skill-in-claude-code/)).

The contradiction warning is the argument that matters most for a name-driven setup, because naming a skill does not protect you from it. If two loaded skills disagree about spacing or type scale, Claude gets both sets of instructions. One relayed and unverified anecdote makes the same point more sharply: a Substack author reportedly tested all 47 skills from a viral list against vanilla output and found 40 made output worse ([responseawareness](https://responseawareness.substack.com/p/scaling-claude-code-skills-without-6a6)). Treat that as a story, not a finding.

## Designers call skills by name because auto-triggering is a coin flip

Anthropic's docs say both routes work by default. You type `/skill-name`, or Claude loads a skill on its own when your request matches its description ([Claude Code skills](https://code.claude.com/docs/en/skills)). Tutorials for designers lean on the automatic route. The workflows designers actually describe use the named route: Halpin types `/setup`, Thrizu has buyers run `/audit-ux`, Dean chains `/discover`, `/strategize` and `/handoff`. Panakkaparambil calls `/impeccable craft` ([Clinton Halpin](https://clintonhalpin.com/blog/using-claude-code-for-product-design/); [solodesign.cc](https://solodesign.cc/blog/claude-code-for-designers/); [MC Dean](https://marieclairedean.substack.com/p/i-built-63-design-skills-for-claude); [hashp](https://hashp.substack.com/p/claude-code-design-skills-a-guided)). No source measures what share of invocations are manual.

The measured data explains the habit. Scott Spence ran about 250 invocations in fresh sandboxes on Sonnet 4.5 with 4 skills and 22 prompts in February 2026. **Baseline auto-activation was 55% and 50% across two runs.** A forced evaluation hook raised it to 100% on easy prompts and 75% on harder ones ([Spence](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals)). By March the hook he had relied on for months stopped being obeyed ([Spence](https://scottspence.com/posts/how-to-make-claude-code-follow-hook-instructions)). Two other details from his tests are worth keeping. When Claude did activate a skill, it never picked the wrong one; the failure was not activating at all. And this happened with only 4 skills, so under-triggering is not caused by library size. The tests are small, unreplicated and tied to one model at one point in time.

Bug reports match. Issue #20986 describes a request that matched a skill's description exactly while Claude did the work by hand, and several similar issues exist ([#20986 mirror](https://claudeissues.com/issue/20986-claude-ignores-skill-triggers-even-when-user-request-clearly-matches-skill-descr)). Practitioners respond by forcing the skill: an explicit `Skill(name)` in the prompt, a CLAUDE.md line telling Claude when to run it or moving must-apply rules into always loaded files ([Spence](https://scottspence.com/posts/claude-code-skills-dont-auto-activate); [HN](https://news.ycombinator.com/item?id=49598293)). Naming skills is the standard workaround, not an eccentric habit.

## A 1% budget deletes descriptions but never names

Anthropic documents two separate costs of a large library, and they stack.

**Attention dilution.** The enterprise guide says each skill's name and description "competes for attention in the system prompt," and with too many active, "Claude may fail to select the right Skill or miss relevant ones entirely." It gives no recommended count. Its advice is to measure recall with evals and **"stop adding when performance degrades"** ([Skills for enterprise](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/enterprise)). The same page names broad descriptions that "steal triggers" from neighboring skills as a known failure. No published data shows how fast recall falls as the count rises.

**Hard truncation.** In Claude Code the skill listing is capped at **1% of the context window** by default (`skillListingBudgetFraction`, fallback 8,000 characters), and each entry is capped at 1,536 characters ([Settings reference](https://code.claude.com/docs/en/settings-reference)). When the listing overflows, "Claude Code keeps every skill's name but drops the descriptions of the least-used skills, so Claude can still invoke those skills but is less likely to choose one on its own" ([Settings reference](https://code.claude.com/docs/en/settings-reference)). That creates a feedback loop: a rarely used skill loses its description, so it fires even less. A maintainer confirmed this is intended ([Issue #81081](https://github.com/anthropics/claude-code/issues/81081)). The live complaint is that it happens silently ([Issue #64606](https://github.com/anthropics/claude-code/issues/64606)).

The counts at which this bites are real. One user at 253 skills had **only 28 keeping their description text** ([Issue #81081](https://github.com/anthropics/claude-code/issues/81081)). Another saw a warning that 81 descriptions had been dropped, with the listing at 3.2% of context against the 1% budget. A commenter on the same issue saw truncation start around 23,000 characters of combined description text ([Issue #68135](https://github.com/anthropics/claude-code/issues/68135)). The threshold is total description length, not skill count.

The token cost itself is bounded. Anthropic puts metadata at about 100 tokens per skill, with the body loading only on use ([Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)). One measurement put 29 skills at about 2,787 tokens of per-session overhead ([tokc](https://pypi.org/project/tokc/)). Because the listing is capped, a big library cannot grow that cost past the budget unless you raise it, and the warning in #68135 says raising it would cost "~6k tokens for skills every session" ([Issue #68135](https://github.com/anthropics/claude-code/issues/68135)). Plugins carry their own wrinkle: an enabled plugin puts every model-invocable skill's description in context on every turn whether you use it or not, and plugin skills cannot be trimmed one at a time. You enable or disable the whole plugin through `/plugin` ([Plugins overview](https://code.claude.com/docs/en/plugins/overview); [Claude Code skills](https://code.claude.com/docs/en/skills)).

Once invoked, skills cost more. A loaded skill body stays in the conversation across turns. After compaction Claude Code re-attaches the first 5,000 tokens of each recently invoked skill within a combined **25,000 token budget**, so "older skills can be dropped entirely after compaction if you have invoked many in one session" ([Claude Code skills](https://code.claude.com/docs/en/skills)). This depends on how many skills a session uses, not how many are installed.

## What this means for a setup like yours

**Is 300 normal?** The count is not. The habit is. No survey sets a baseline, but among the few people with measured counts, all of them heavy users who hit a bug, 300 is at the top. Among designers who describe their setups, the norm is single digits. The pattern of a large installed set with a small used set is common, though: the 255 skill user had usage history on 44. Calling skills by name or through your own presets matches what designers who describe real work do, and it is the standard workaround for unreliable auto-triggering.

**Does the count affect skills you name?** Mostly no. Names always stay in the listing, so `/skill-name` works at any count, and so does a prompt that names the skill, since Claude can still invoke a skill whose description was dropped. What the count degrades is automatic triggering for requests where you do not name a skill. Those requests are the ones exposed to dilution and truncation, and with 300 installed most descriptions are almost certainly being dropped. That is my inference from the reported cases, not a measurement of your machine.

Four things still apply when you name skills. First, the listing takes up to 1% of context on every turn, plus whatever your enabled plugins add, even when you name only one skill. Second, overlapping design skills contradict each other once loaded, and a preset that chains several from different packs is exactly how that happens. Third, a preset that loads many skill bodies in one session runs into the 25,000 token compaction budget. Fourth, Claude Code expands a stacked invocation as the first skill "plus up to five more," so a preset that stacks more than six slash commands in one message will not load them all ([Claude Code skills](https://code.claude.com/docs/en/skills)).

**One trap if you prune.** The obvious way to cut listing cost can break the way you work. `disable-model-invocation: true` and the `skillOverrides` value `"user-invocable-only"` both hide a skill from Claude. A typed `/skill-name` still works, but a prompt that names the skill in prose, or a preset that asks Claude to invoke other skills through the Skill tool, would no longer reach it ([Claude Code skills](https://code.claude.com/docs/en/skills)). For skills you call by name in prose or through presets, `"name-only"` is the safe override: the name stays visible and only the description goes. The catch is that overrides do not reach plugin skills, and most of a pack-heavy library lives in plugins.

## Conclusion

The question of how many skills is the wrong unit. The reports point to total description length, and to whether a skill is ever invoked, as the measures that decide behavior. Anthropic's 2026 tooling formalizes pruning by usage: `/skill-doctor` reports what each skill costs and flags ones never invoked, and `/doctor` estimates the listing cost and suggests disabling unused plugins ([Claude Code skills](https://code.claude.com/docs/en/skills); [Measure plugin cost](https://code.claude.com/docs/en/plugins/measure)). For a name-driven user the payoff from pruning is smaller than the docs imply, because naming already bypasses the failure the budget creates. The case for pruning is about contradiction and per-turn cost, not about losing access to named skills.

The more useful move for a setup like this is to keep the library as it is and let the usage data decide. Run `/skill-doctor` and you will see which plugins hold skills you never call. Disabling those whole plugins removes their per-turn cost and their chance of loading contradictory guidance. The skills you rely on stay exactly as reachable by name as they are now.
