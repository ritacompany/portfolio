# Build the Haven row yourself, borrow three references

The best approach for the Haven ending is a hand built CSS grid accordion in plain HTML, CSS and about 60 lines of vanilla JavaScript, modelled on the CodeFronts `:has()` horizontal accordion for layout, Framer's ExpandFrame for motion and touch behavior and Frameze's Reveal Gallery Pro for its keyboard contract. Nothing on the market is worth installing: every Framer Marketplace candidate is a no-code layer tree with no readable source, the React libraries (Aceternity, Cult UI, Skiper, 21st.dev) solve a different problem (morph a card into a modal or blur its siblings) and the pure CSS demos that do solve "one grows, others shrink, caption appears" all skip at least one of touch, keyboard or reduced motion. The bigger risk is not the component but the content model. Hover gated text is weak on discoverability and invisible to touch and many keyboard users ([NN/g](https://www.nngroup.com/articles/flat-design-best-practices/)), and this row is the last thing a skimming recruiter reads, so the spec below keeps a short title and need tag visible on every card at rest, opens the first card by default so one sentence is always on screen and drops the accordion entirely below 900px in favor of the scroll snap strip the current `haven-ending-final.html` study already uses, with every caption visible. The result reads as one confident gesture on a laptop and never hides the argument from anyone else.

## Ten Framer listings fit, none ships code you can port

The Framer Marketplace has at least ten direct matches, and five are close to this brief. **ExpandFrame** (Haseeb Aamir, $5 on the listing body, "free" in the search title, so price is unconfirmed) is the most complete: hover on desktop or tap on mobile expands an image while the others "smoothly contract and dim", with a per item label and link, a separate mobile expansion amount and an optional reset when the cursor leaves ([ExpandFrame](https://www.framer.com/marketplace/components/expandframe/)). **Image Strip Expander** ($5) is the only other listing that explicitly switches from hover to click on mobile, and it adds a dock style neighbor falloff where cards next to the active one widen slightly ([Image Strip Expander](https://www.framer.com/marketplace/components/image-strip-expander/)). **AccordGallery** ($10, max six images) has caption reveal built in ([AccordGallery](https://www.framer.com/marketplace/components/accordgallery/)), **Expandable Cards** by Zaid ($5) claims spring motion on hover or click ([Expandable Cards](https://www.framer.com/community/marketplace/components/expandable-cards/)) and **Expanded Card** (free) can be copied into Framer so its variants are inspectable at no cost ([Expanded Card](https://www.framer.com/marketplace/components/expanded-card/)).

**No Marketplace listing documents keyboard or focus behavior**, and none publishes spring parameters. Third party sellers are thinner, but Frameze is the exception that matters: **Reveal Gallery Pro** ($8) documents Tab, Enter or Space to expand, Arrow keys between panels and Escape to collapse, plus swipe on touch ([Reveal Gallery Pro](https://frameze.com/components/reveal-gallery-pro)). It expands panels edge to edge rather than within a row, so it is too heavy for Haven, but its keyboard model is the best written contract found anywhere. Frameze's **Cards Hover Section** contributes a "pure CSS" neighbor dimming falloff ([Cards Hover Section](https://frameze.com/components/cards-hover-section)).

Porting any of these means rebuilding from the preview, since a published Framer page exports compiled React bundles, not source. That makes the purchases worth nothing as code and something as motion references. One caution on all of the above: no preview was hands-on tested during research, so "most refined" rests on seller copy until you open them side by side.

## Pure CSS accordions port as is, React libraries do not

Open source candidates split into two families. The first, flex or grid "image accordions", is almost entirely pure CSS under MIT and drops straight into a static page. The **CodeFronts Horizontal Accordion Expand** is the strongest base: a CSS grid rail where `:has()` rewrites `grid-template-columns` (for example `2.6fr 1fr 1fr 1fr 1fr` when the first panel is hovered), every `:hover` rule is paired with `:focus-within`, panels are natively focusable links, reduced motion collapses durations to near zero and the page recommends a hidden radio per panel so a tap can pin a panel open ([CodeFronts](https://codefronts.com/components/css-animated-cards/horizontal-accordion-expand/)). Grid track lists interpolate as long as the track count stays fixed, which is exactly the five card case. Its sibling **Zoom-on-Hover Expanding Accordion** uses `flex: 1` to `flex: 5` with captions entering from `opacity: 0` and `translateY(12px)` ([CodeFronts](https://codefronts.com/components/css-image-slider/zoom-on-hover-expanding-accordion-gallery/)), and the **fyildiz1974** CodePen (MIT, March 2026) goes `flex: 1` to `flex: 3` over 0.5s, uses `:active` for touch, ships a reduced motion block and, below 468px, stacks cards with captions permanently shown ([CSSScript](https://www.cssscript.com/responsive-expandable-cards-accordion-slider/), [CodePen](https://codepen.io/fyildiz1974/pen/RNRwEjr)). Brad Traversy's **50 Projects 50 Days Expanding Cards** has no focus or reduced motion handling, but it contains the single most useful timing trick: the caption's opacity transition is delayed 0.4s so text appears only after a 700ms panel growth has mostly settled, which stops words reflowing inside a widening box ([style.css](https://raw.githubusercontent.com/bradtraversy/50projects50days/master/expanding-cards/style.css)).

The second family is React with Motion, and it solves a different job. **Aceternity Expandable Card** and **Apple Cards Carousel** morph a card into a centered modal through `layoutId`, with no aria attributes and no reduced motion check in the source ([Expandable Card source](https://ui.aceternity.com/registry/expandable-card-demo-standard.json), [Apple Cards Carousel source](https://ui.aceternity.com/registry/apple-cards-carousel.json)), under a proprietary licence that bars redistributing source ([Aceternity licence](https://ui.aceternity.com/licence)). **Aceternity Focus Cards** blurs non-hovered siblings with mouse events only and is about ten lines of class toggling, trivially rewritten as one `:has()` rule ([Focus Cards source](https://ui.aceternity.com/registry/focus-cards.json)). Cult UI's MIT **Expandable** and **ExpandableScreen** ([Cult UI](https://www.cult-ui.com/docs/components/expandable)), the 21st.dev **Gallery Modal Accordion** with no stated licence ([21st.dev](https://21st.dev/@uilayout.contact/components/gallery-modal-accordion)) and Skiper UI's Pro **Projects Showcase** ([Skiper](https://skiper-ui.com/v1/skiper80)) all need a full rewrite. The one vanilla option with real shared element motion is motion.dev's **App Store layout** example, but its `animateLayout` sits behind Motion+ ([motion.dev](https://motion.dev/examples/js-app-store-layout)). For a one sentence caption beside a phone, a modal morph is the wrong pattern anyway; it is built for long content.

| Candidate | Stack | Hover, focus, touch, reduced motion | Port to the portfolio |
|-|-|-|-|
| CodeFronts `:has()` grid accordion | Pure CSS, MIT | All four covered or guided | Copy, restyle |
| fyildiz1974 accordion slider | Pure CSS, MIT | All four, captions always on at narrow widths | Copy, restyle |
| CodeFronts flex zoom accordion | Pure CSS, MIT | No touch handling | Copy, add tap |
| 50 Projects Expanding Cards | CSS plus click JS | Click only, no focus or reduced motion | Borrow caption delay only |
| ExpandFrame, Image Strip Expander | Framer no-code | Hover and tap, keyboard unstated | Rebuild from preview |
| Reveal Gallery Pro | Framer no-code | Full keyboard and swipe | Copy the keyboard contract |
| Aceternity, Cult UI, Skiper, 21st.dev | React plus Motion | Mouse first, weak accessibility | Full rewrite, wrong pattern |

## Live sites use this on studio reels, rarely in case studies

The grow in row pattern lives mostly on production company, studio and luxury product sites where imagery is the content and the caption is a credit. Awwwards Inspiration lists a horizontal accordion with quotes on **OSAIC** ([Awwwards](https://www.awwwards.com/inspiration/horizontal-accordion-osaic)), a dark fleet gallery on **Maiora** whose deep link now redirects ([Awwwards](https://www.awwwards.com/inspiration/horizontal-accordion-maiora)), a hover video slider on **Accordion Productions**, confirmed live with a numbered project list carrying credits text ([Awwwards](https://www.awwwards.com/inspiration/image-video-slider-accordion)) and a responsive vertical accordion on **OSI** that shows how the pattern survives narrow screens ([Awwwards](https://www.awwwards.com/inspiration/vertical-accordion-osi)). The one designer portfolio inspected live, **Camila Rosa**, keeps every project name visible at rest and uses hover only as flourish ([Awwwards](https://www.awwwards.com/inspiration/project-card-hover-camila-rosas-portfolio)).

Two signals follow. First, case study authors largely avoid hiding their summary text behind hover, which is evidence about the reading task, not just taste. Second, three of the Awwwards links (Maiora, Fifth Year, Stefano Bartoletti) are dead or redirected within one to three years, which weakly suggests heavy custom hover components get retired. Exact easing and width ratios for these sites were not measured because the components are JavaScript driven, so treat them as mood references, not timing references.

## Hover hidden text costs skimmers four fifths of the ending

NN/g treats hover triggered reveals as weak signifiers that "require interaction effort" and reduce discoverability ([NN/g](https://www.nngroup.com/articles/flat-design-best-practices/)), and in its navigation study a homepage whose descriptions "appeared only on hover" left people vague enough to fall back to the menu ([NN/g](https://www.nngroup.com/articles/find-navigation-desktop-not-hamburger/)). Input detection does not rescue this: `hover` and `pointer` media queries report only the browser's guess at a primary input, devices are often touch and mouse at once and keyboard users cannot be detected at all ([CSS-Tricks, Patrick Lauke](https://css-tricks.com/interaction-media-features-and-their-potential-for-incorrect-assumptions/)). Applied to Haven, a pure reveal means a skimmer who never hovers reads none of the five sentences that prove the "understood and safe" statement. That is why the recommendation keeps titles and need tags always visible and one card open by default. The stricter alternative, all five sentences visible with hover only emphasizing, remains defensible; choose it if the sentences are the argument rather than its support.

The standards set the rest of the contract. NN/g's timing guidance is 0.1s feedback, a 0.3 to 0.5s pause before revealing hidden content and at least 0.5s before hiding it after the cursor leaves; taps should respond in 0.1s and stay open until the user acts elsewhere ([NN/g](https://www.nngroup.com/articles/timing-exposing-content/)). WCAG 2.2 SC 1.4.13 requires hover or focus content to be dismissible, hoverable and persistent ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html)); a caption inside the growing card arguably sits outside its popup scope, but supporting Escape and persistence costs nothing. SC 2.3.3 counts size changes as motion while excluding opacity, color and blur ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)), so under reduced motion the width change must snap and only a fade may remain, consistent with web.dev naming scale and zoom as vestibular triggers ([web.dev](https://web.dev/articles/prefers-reduced-motion)). Heydon Pickering's card guidance supplies the markup rules: a heading as each card's main content, `:focus-within` mirroring hover and one interactive target per card ([Inclusive Components](https://inclusive-components.design/cards/)). Finally, `@media (hover: hover)` prevents sticky hover on touch, and `any-hover` catches an iPad with a mouse ([Jacob Padilla](https://jacobpadilla.com/writing/hover-media-query)), but the spec below decides per event with `pointerType` instead of trusting either.

## The interaction spec for the Haven row

The numbers assume the current study's 1440px max width, 40px gutter, Satoshi on the near black background and the site's existing `cubic-bezier(0.22, 1, 0.36, 1)` ease. Content width is 1360px. Values marked "judgment" are design calls inside the sourced ranges, not sourced figures.

**Structure.** A `ul` of five `li` cards in a CSS grid row. Each card holds its own color field, the phone screenshot, an `h3` title of two to four words (for example "Identity quiz"), a need tag reading "Understood" or "Safe" and the one sentence caption as a `p` with an id. A `button` wraps the title, carries `aria-describedby` pointing at the caption and stretches over the whole card with a pseudo element, so each card is one target. Captions never use `display: none` or `visibility: hidden`; they hide with opacity only, so screen readers always read all five and no `aria-expanded` is needed, because nothing is hidden from assistive technology. Screenshots get real alt text.

| Property | Wide screens (900px and up) |
|-|-|
| Row | Fixed height 520px, gap 16px, so section height never changes |
| Tracks | Active card `2.6fr`, others `1fr`: about 511px active and 196px resting at 1360px |
| Default state | Card one (identity quiz) open at rest, so one sentence is always visible |
| Phone | Fixed 176px wide in every state, top aligned, never scaled; only the color field grows around it |
| Caption | Fixed 240px measure beside the phone in the open card, Satoshi 16px on 1.4 line height, so text never reflows during growth |
| Grow | `grid-template-columns` over 450ms with the site ease (judgment, inside the 0.5s to 0.7s range of the references) |
| Caption in | Opacity 0 to 1 and 8px rise over 250ms, delayed 200ms after grow starts (the Traversy delay, scaled down) |
| Caption out | Opacity to 0 over 120ms, no delay, before the card shrinks |
| Siblings | Resting cards' screenshots drop to 55% opacity while another card is open; color only, so not motion under 2.3.3 |
| Title and tag | Always visible on every card at full contrast |

**Mouse.** JavaScript handles `pointerenter` only when `pointerType` is mouse. Entering the row from outside waits 300ms before the first change (NN/g's lower bound). Moving between cards once the row is engaged waits 150ms, so a sweep across five cards does not flicker (judgment). Leaving the row holds the current card for 500ms, then returns to card one. Clicking with a mouse does nothing extra.

**Touch.** At 900px and up (tablets), the first tap on a card opens it immediately with no intent delay and it stays open until another card is tapped; there is no hover and no navigation on tap. Below 900px the accordion is off: the row becomes the existing scroll snap strip at 72% card width, every card shows its title, tag, phone and full sentence with no motion involved. Swipe is plain native scrolling, not a gesture the component interprets.

**Keyboard.** Tab moves card to card; focusing a card opens it instantly with no intent delay and a visible `:focus-visible` ring on the card. Left and Right arrows move focus between cards as a convenience, Escape returns the row to the default card and Enter or Space does nothing new because focus already opened the card. This is Frameze's contract minus Enter to expand.

**Reduced motion.** Under `prefers-reduced-motion: reduce` the track change is instant, the caption crossfades in 150ms with no rise, the intent delays stay (they are timing, not motion) and no screenshot ever scales or zooms.

**Implementation note.** Drive state from one `data-active` attribute on the `ul`, set by the JavaScript for mouse, tap, focus and Escape, and map it to five `grid-template-columns` rules in CSS. That keeps one source of truth instead of the CodeFronts mix of `:hover`, `:focus-within` and radio state, and it is what makes the intent delays possible. Animating grid tracks triggers layout each frame, which is cheap at five cards; if it stutters on a low end laptop, switch to fixed widths with a transform based FLIP.

## Conclusion

The research reframes the question. The component is a solved problem of about a day, and every off the shelf option is either uninstallable on a static site or weaker on accessibility than what a careful hand build gets for free. The real decision is editorial: whether the five sentences are support for the closing statement, in which case the reveal spec above is right, or the closing argument itself, in which case they belong on screen at rest and the cards should only emphasize. The spec defaults to the first because the brief asks for a reveal, but it is built so that flipping to always visible means deleting one opacity rule, not redesigning the row.

Open these first, in this order. **CodeFronts Horizontal Accordion Expand** is the code base to copy: [codefronts.com/components/css-animated-cards/horizontal-accordion-expand](https://codefronts.com/components/css-animated-cards/horizontal-accordion-expand/). **ExpandFrame** is the motion and sibling dimming bar to match: [framer.com/marketplace/components/expandframe](https://www.framer.com/marketplace/components/expandframe/). **fyildiz1974's accordion slider** shows the caption slide up and the always visible narrow layout: [codepen.io/fyildiz1974/pen/RNRwEjr](https://codepen.io/fyildiz1974/pen/RNRwEjr). **Reveal Gallery Pro** demonstrates the keyboard contract live: [revealgallerypro.framer.website](https://revealgallerypro.framer.website/). **Image Strip Expander** is worth a look for the hover to tap switch and the neighbor falloff, which is the one enhancement to consider after the base is built: [base-imagestripexpander.framer.website](https://base-imagestripexpander.framer.website).
