# Capture the before, then publish the tokens

The single most important move is about timing, not effort: **five pieces of case study evidence exist only until the token publish and the MVP rebind, and none of them can be rebuilt afterwards.** They are the first run of the agent usability test against the library agents can see today, the raw output the Figma MCP server hands an agent today, the Dev Mode view a developer sees today, binding coverage on a fixed set of MVP screens before the rebind and dated words from developers about building from Figma now. Capture all five before the publish. After that, the cleanup comes down to a short list of calls only Chadwick can make (his yes to the tokens chat's steps 1 to 4 once it shows the 17 to 19 Oct work, the colour mapping review, the spacing links with no role and the 14 Oct restructure entry for the decision log). Sessions can do everything else. The library is already further along than the 1 Oct audit suggested: **code syntax went from 0 of 235 variables to 421 of 424, component descriptions from 4 of 94 to 101 of 107 and every one of the 128 published variables now has a scope, a description and a web code name** ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). What still separates it from a system worth a case study is wiring. **Only 69.0% of colour in library components lands on roles, 798 colour properties still point at hidden primitives and just 6.7% of gaps and 1.9% of paddings are bound** (same source). Then there is proof that the system reaches code. Figma's own docs name Code Connect as "the most effective way to get your agent to reuse your real components", and it works on Mondai's Professional plan without GitHub ([Figma, Structure your Figma file](https://developers.figma.com/docs/figma-mcp-server/structure-figma-file/); [Code Connect UI setup](https://developers.figma.com/docs/code-connect/code-connect-ui-setup/)).

The research supports the 15 Oct plan's three acts and its framing of a system built for two audiences (the people who use the product and the agents who build it) ([PR #177](https://github.com/ritacompany/mondai/pull/177)). Act 2 (agents failed in ways that looked right) is exactly the "what didn't work" that Etsy's hiring managers ask every case study to show ([Etsy guide](https://extfiles.etsy.com/CareersPage/ProductDesign.pdf)). A live September 2026 lead posting makes "defining how AI agents can correctly compose UIs from its components" a core duty ([Cox Enterprises posting](https://designproject.io/jobs/lead-product-designer-design-foundations-interstate-at-cox-enterprises-dtaqds)). That is one posting, not a trend, and no hiring source has tested the framing itself. The research sharpens the plan in two places. First, its table of what agents read lists descriptions and property names but leaves out Code Connect, which Figma ranks first; and no Figma page opened confirms that component descriptions or variable code syntax reach an agent at all ([ai ready systems notes](../research_notes/Design%20system%20case%20study%20readiness/ai-ready-systems.md); [claim check](../research_notes/Design%20system%20case%20study%20readiness/claim-check.md)). Second, "before the token publish" has a precise meaning: the before is the library a consumer sees, not the library file. The research contradicts the plan nowhere. Two Figma tools the notes discuss, Library Analytics and Check designs, are Organization and Enterprise features, so on Professional the plan's own hard coded value check and the existing page scan are the measurement route, not a fallback.

## Cleaning up the library: four calls are his, the rest is session work

Ranked by what unblocks the most, perishable first.

1. **Perishable. Before the publish, save a named version of the library and duplicate both the library and the MVP file. Write the publish description as release notes.**
   Reason: the publish and the MVP rebind overwrite the state every before and after in this report compares against, and the publish is the system's first versioned release worth showing. Nothing is logged change by change today. There is no changelog, and whether any "Dev pulled" named versions exist could not be read ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). Library publish descriptions appear in version history and suit "high level change summaries" ([Figma, Add descriptions](https://help.figma.com/hc/en-us/articles/7938814091287)). The plan already proposes a named version saved before any publish, tested before it is relied on ([PR #177](https://github.com/ritacompany/mondai/pull/177)). The tokens chat does this as part of its publish step; it is not new work for another chat.
   What would change it: if a named version on Professional proves fully restorable and is kept indefinitely (not checked; see unknowns), the duplicates become redundant.

2. **The tokens chat restates what his yes to steps 1 to 4 now covers, including the 17 to 19 Oct work, before he answers.**
   Reason: the waiting line in the working log dates from 15 Oct. The branch has since recorded 44 new colour roles, renames, an 18 Oct revert of visible 17 Oct colour changes and the 2 Oct spacing ladder restored on 19 Oct, all described as built "from the accepted proposal" ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md); [PR #179](https://github.com/ritacompany/mondai/pull/179)). On 15 Oct he found a record that said work was done when he could not see it ([PR #177](https://github.com/ritacompany/mondai/pull/177)). A yes given against a stale summary repeats that failure, and it is the failure Act 2 is about.
   What would change it: nothing; the restatement costs the tokens chat one message.

3. **His three calls inside steps 1 and 2: the colour mapping review, the roughly 390 spacing links whose values have no role and approval of the drafted 14 Oct restructure entry for the decision log.**
   Reason: these are the only parts of the cleanup that turn on his judgment. Of 9,784 raw colour links in the mapping draft, 7,914 have a role with the same value; the other 1,870 need a call on meaning. Until then, 798 colour properties in library components keep pointing at primitives the picker hides ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). That is the failure Romina Kavcic recorded in one informal run: an agent given tokens used `red.6`, `space-2` and `neutral-7` because it "had no way to know that `red-6` is a primitive" ([The Design System Guide](https://learn.thedesignsystem.guide/p/design-tokens-that-ai-can-actually)). The 14 Oct entry matters beyond tidiness. The plan makes the restructure the turning point of the story, and today no decision log entry records it ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). The tokens chat owns the drafts and its pick for each; this report does not redo them.
   What would change it: if the colour mapping draft's same value matches turn out to be wrong by meaning in his review, step 2 grows and the publish date moves.

4. **Publish once, then rebind the MVP file and clear the stray links (step 4: 15 links to retired variables and 239 to other or older libraries on the Mobile workspace), only after the five befores in the next section are captured.**
   Reason: this is the order the 15 Oct token audit set ("publish once and rebind the MVP file") and the plan's wave 0 ([PR #179](https://github.com/ritacompany/mondai/pull/179); [PR #177](https://github.com/ritacompany/mondai/pull/177)). The befores do not block his yes or the local work in steps 1 to 3, because they read the published library and the unrebound MVP file. They block only the publish itself.
   What would change it: if the before captures slip, the publish waits; never the other way round.

5. **After the publish, a session fixes the defects that agents read and screenshots show: 13 sets with a property still named "Property 1", "Variant2", "Select Hover" beside "Selected hover", "Press" beside "Pressed", "Black alt.", the duplicate Scrollbar sets, eight properties with only one value, title case property names, the six components with no description and the Grids & spacing board that still shows a gutter of 32 against the decided 24.**
   Reason: Figma uses component descriptions in search and shows them in Dev Mode Inspect ([Figma, Add descriptions](https://help.figma.com/hc/en-us/articles/7938814091287)), and Figma names clear naming as an output improver for agents ([Structure your Figma file](https://developers.figma.com/docs/figma-mcp-server/structure-figma-file/)). The plan puts these after the publish so the tokens chat's change count stays clean ([PR #177](https://github.com/ritacompany/mondai/pull/177)). Defect list and counts from ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)); board status from ([SOURCES](../reference/design-system-cs/SOURCES.md)).
   What would change it: if the agent test's first run shows property names cause no agent mistakes, these drop in rank for agents but stay for human readers and screenshots.

6. **The tokens chat unifies the three retirement words into one convention, with the replacement named in each description.**
   Reason: the file uses "Retired/" on 129 variables, "Deprecated/" on six and "Retiring/" on two ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). The token format standard gives deprecation its own field with an optional reason ([DTCG Format Module 2025.10](https://www.designtokens.org/tr/2025.10/format/)). One word plus a "use instead" line is a governance signal a reviewer reads in seconds.
   What would change it: if the 129 retired variables are deleted after the MVP rebind, only the six and two remain to rename.

7. **The lead chat writes the five picks of #177 into the plan file so his answer has a record.**
   Reason: the plan says the picks are "in the chat message that delivered this plan", and no file, PR body or commit holds that message ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). A decision that lives only in a chat is the same gap the case study's evidence rule cannot trace.
   What would change it: nothing; it is session work.

## Start capturing now: five befores vanish at the publish

Ranked by how completely each is lost once the publish and rebind happen. Items 1 to 5 are perishable.

1. **Perishable. Run the agent usability test's first run before the publish, reading the published library from a fresh file, and save the raw MCP output with it.**
   Reason: the test is the plan's one measurable experiment, and it has not run ([PR #177](https://github.com/ritacompany/mondai/pull/177)). Three details decide whether it holds up later. (a) The before is what an agent sees today. Agents find library content through `search_design_system` and `get_libraries`, which read connected, published libraries ([Figma, Tools and prompts](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)). The library file itself already carries unpublished code syntax and descriptions ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). So the agent works in a new file with the library enabled, not inside the library. That is my reasoning, because publish state could not be read. (b) Save the raw output of `get_variable_defs`, `get_design_context` and three `search_design_system` queries on the known screen. That output, before and after, settles the question no Figma page answers: whether code syntax and descriptions reach the agent at all ([ai ready systems notes](../research_notes/Design%20system%20case%20study%20readiness/ai-ready-systems.md)). (c) Fix the screen, prompt, model and defect categories in writing before the run, record the model version and run time and run it three times. Agent output varies from run to run, so one before against one after could differ by chance; that is my reasoning, not a source. Report results as counts ("raw values: 3 of 3 runs"), never percentages, the standard the portfolio already uses for small samples ([Case study results without metrics](Case%20study%20results%20without%20metrics.md)).
   What would change it: if the publish has already happened when this runs, the before is gone and the test becomes an after only, measured against the 1 Oct audit as a weaker baseline.

2. **Perishable. Screenshot Dev Mode Inspect on one component and one screen today, showing the names a developer reads now.**
   Reason: code syntax "will appear in code snippets in Dev Mode when inspecting elements using the variable" ([Figma, variables and code syntax](https://help.figma.com/hc/en-us/articles/15145852043927-Create-and-manage-variables-and-collections)). After the publish the same panel should read `var(--color-neutral-600)` and its siblings. A matched pair of images is the clearest before and after the system has, and one of Indeed's hiring managers asks for "the 'before' if there was one" ([Indeed Design](https://indeed.design/article/ux-design-portfolio-advice-from-hiring-managers/)). The colour chat working on the case study's light design system decides how these dark frames sit on the page; capture them raw and full size so it has what it needs.
   What would change it: if developers do not use Dev Mode (unknown), the MCP output in item 1 becomes the developer side before instead.

3. **Perishable. Run the existing page scan on a fixed, named set of MVP handoff pages before the rebind, alongside the library scan.**
   Reason: today's measurement covers library components only. The screens are what the rebind changes. The 1 Oct audit's Home page had 0% of 1,835 gaps linked ([SOURCES](../reference/design-system-cs/SOURCES.md)), and the Mobile workspace still holds 15 retired and 239 stray links plus local copies of seven Calendars sets ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). Pinterest's adoption measure, the share of a page's layers that come from the library, needs only reads of the files, not an Enterprise feature ([Figma, Pinterest adoption](https://www.figma.com/blog/how-pinterests-design-systems-team-measures-adoption/)). Library Analytics would have given usage history, but it is not on Professional, so a dated scan is the only usage record that will ever exist.
   What would change it: if the item 1 duplicates of the MVP file survive untouched, the scan could run later on the duplicate. Running it now costs one session and removes the risk.

4. **Perishable. Chadwick asks the developers three short questions this week and keeps their answers dated and in their own words. He also asks for the list of code component paths.**
   Reason: whether developers built from the library is the case study's widest gap; no message from them exists in the sources ([GAPS](../reference/design-system-cs/GAPS.md), item 10). Developers work from Figma with no GitHub access ([SOURCES](../reference/design-system-cs/SOURCES.md)), so their side of the before is only in their heads, and memory of a before fades once the after arrives ([impact metrics notes](../research_notes/Design%20system%20case%20study%20readiness/impact-metrics.md)). Suggested questions: what do you do when a Figma value has no token name; what do you ask the designer most often; how long does one screen take you to build from Figma. The path list feeds Code Connect (next section) and is itself adoption evidence: it shows which library components have a code twin. This is his to do because it rests on his relationship with the team; a session drafts the message.
   What would change it: if a developer message from before the cleanup turns up in Discord or chat, it covers part of the before and the questions shrink to the after.

5. **Perishable. Start a veto log today and pull the October rejections into it while his words are still easy to find.**
   Reason: the story's second act is agents producing work that looked right and his rejecting it. The record has the moments: on 20 Sep nine screens passed a token check and he rejected them, on 15 Oct he said "this work never happened" and on 18 Oct visible 17 Oct colour changes were reverted ([PR #177](https://github.com/ritacompany/mondai/pull/177); [current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). His conversation corpus stops at September ([SOURCES](../reference/design-system-cs/SOURCES.md)), and the plan takes up a proposal to archive about 170 finished chats. One line per veto (date, what the agent produced, what he rejected, why, what check or rule changed) is the evidence that makes AI work credible. The 2026 guidance, from a generic content site and a vendor, converges on this: disclose AI in the process section with the tool's role, your ownership and evidence the reader can check ([Learnist](https://www.learnist.org/how-to-disclose-ai-tools-in-portfolio/)), because "Hiring managers hire the diagnostician" ([Lovart](https://www.lovart.ai/blog/ai-design-portfolio-interview-2026)). One reviewer of 500 applications turns down work "that looks vibed" ([Tom Scott](https://verifiedinsider.substack.com/p/learnings-from-reviewing-500-design)). A session can keep the log; only the reasons need his words, and most are already quoted in PR bodies and the decision log.
   What would change it: if he frames the AI sessions as background rather than story (his call, item 7), the log still earns its keep as the evidence behind every row now marked ASSUMED.

6. **Record what was deliberately not built, and why, while the reasons are fresh.**
   Reason: one hiring manager in NN/g's survey of 204 hiring professionals put it as "I'm curious to know what isn't in the design and why" ([NN/g](https://www.nngroup.com/articles/ux-design-portfolios/); quoted as one respondent per the [claim check](../research_notes/Design%20system%20case%20study%20readiness/claim-check.md)). This system has real omissions with reasons: dark only (decided 2 Oct), no component tier tokens (only 52% of systems have them, [zeroheight 2026](https://report.zeroheight.com)), no shadow or elevation styles, TDesign icons still in place and no usage analytics on the plan. A session drafts it from the decision log; he confirms the reasons that are not written down.
   What would change it: if any omission gets built before the case study is written, it moves from this list to the after.

7. **His one framing call: how the AI sessions are presented.**
   Reason: every row of Figma execution since September is marked ASSUMED until he decides this ([SOURCES](../reference/design-system-cs/SOURCES.md); [GAPS](../reference/design-system-cs/GAPS.md), item 2). The #177 framing has already half answered it, because agents are the second audience, not hidden help. Recommendation: present it as he wrote the rules, checks and vetoes and agents executed, disclosed in the process section, not as a disclaimer at the top ([Learnist](https://www.learnist.org/how-to-disclose-ai-tools-in-portfolio/)). That turns the ASSUMED rows into CONFIRMED direction with a named executor. The same goes for Teresa's and Nandita's parts (GAPS items 1 and 3), which Etsy's "who you partnered with" asks for anyway ([Etsy guide](https://extfiles.etsy.com/CareersPage/ProductDesign.pdf)). This is not perishable, but every later draft depends on it.
   What would change it: his answer; this is a positioning choice only he holds.

## Set up the system to show what reviewers look for

Hiring sources ask a design system case study for a goal and a measured outcome, the reasoning behind choices, a named role, what did not work and, for systems, proof the library "at some point" became code ([hiring signals notes](../research_notes/Design%20system%20case%20study%20readiness/hiring-signals.md); [Smashing, Dan Donald](https://www.smashingmagazine.com/2022/04/artifacts-design-systems/)). Ranked by how much each one adds to that story.

1. **Components wired to roles: colour by meaning and spacing and radius by value, with the library scan as the scoreboard.**
   Reason: hidden primitives and scoped roles are now in place, but the components still decide what an agent copies. Today the picker tells the truth and the components do not. Buttons & chips has 0 of 218 gaps and 0 of 297 paddings bound; Calendars 0 of 418 and 0 of 352 ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). The industry line between a ready system and a library is whether it carries intent a machine can read and matches what ships ([ai ready systems notes](../research_notes/Design%20system%20case%20study%20readiness/ai-ready-systems.md)). This is the tokens chat's step 2 and the publish that follows; the case study's job is to keep the before and after numbers from the same scan.
   What would change it: if the agent test shows agents ignore component bindings and read only the picker, wiring drops below Code Connect. That is unlikely, because `get_variable_defs` returns what a selection actually uses ([Tools and prompts](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)).

2. **Code Connect UI mappings for every library component that has a code twin, each with custom instructions for agents.**
   Reason: Figma calls Code Connect "the most effective way to get your agent to reuse your real components" ([Structure your Figma file](https://developers.figma.com/docs/figma-mcp-server/structure-figma-file/)). It is available on Professional with one active library and one framework. It needs a Dev or Full seat but no GitHub, since paths can be typed by hand. "All mappings are shared with the Figma MCP server", custom instructions included ([Code Connect UI setup](https://developers.figma.com/docs/code-connect/code-connect-ui-setup/)). It answers three case study needs at once: proof the system became code (Donald), developer adoption evidence (GAPS item 10) and the one confirmed channel where per component usage prose reaches an agent. The plan's agent readability table should gain it. Inputs come from the developer path list (previous section, item 4).
   What would change it: if developers have no shared component code to map, this becomes a statement of the gap and the case study's code parity claim shrinks to code names on tokens.

3. **Versioned releases: a named version and a release note in the publish description on every publish, plus one changelog board in the library file.**
   Reason: Brad Frost's governance process ends each change with "the changelog will be updated" and a release ([Brad Frost](https://bradfrost.com/blog/post/a-design-system-governance-process/)). 56% of system teams publish release notes ([zeroheight 2026](https://report.zeroheight.com)). The team's agreed change check already relies on named versions for developer pulls ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). With no analytics on the plan, version history is the system's governance record, and it only exists if each publish writes into it. Minutes per publish.
   What would change it: nothing in the sources; the cost is too low to defer.

4. **One repeatable measurement, run on the library and the fixed screen set at every publish, kept as a dated table.**
   Reason: credibility comes from a dated baseline, a stated method and honest limits more than from a big number ([impact metrics notes](../research_notes/Design%20system%20case%20study%20readiness/impact-metrics.md)). The system already has two readings by the same method, 1 Oct and 19 Oct ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)), so this is a habit to keep, not a tool to build. Pair the one hard number with the developer quotes and the agent test counts. Do not borrow Figma's 34% or Sparkbox's 47% as Mondai's result: Figma's gives no sample size and calls itself "the maximum time savings one would find", and Sparkbox's rests on 8 developers building one form ([claim check](../research_notes/Design%20system%20case%20study%20readiness/claim-check.md); [Sparkbox](https://sparkbox.com/foundry/design_system_roi_impact_of_design_systems_business_value_carbon_design_system)).
   What would change it: if the plan moves to Organization, Library Analytics and Check designs add usage history and a lint count. Neither is available now.

5. **Usage intent written into the system itself, not only into the skills: "use for" and "do not use" in descriptions, property names that match the state words and the Code Connect instructions.**
   Reason: the agent test runs with only the library and no skills ([PR #177](https://github.com/ritacompany/mondai/pull/177)), so anything an agent needs to build correctly has to live in the library. That is the test's strength and the reason the plan's framing holds. Practitioner guidance agrees that a token file "can list every color and spacing value in a product without explaining where any of them belong" ([Southleft](https://southleft.com/insights/design-systems/machine-readable-design-tokens-for-ai-ready-component-libraries/)). Figma's own advice for Make kits is short imperative rules ("Do not use small text for anything except captions") ([Figma, Make kit guidelines](https://help.figma.com/hc/articles/43602393097239)). Published variables already carry descriptions; components carry purpose but the do not lines are the gap the test will expose.
   What would change it: if the before and after MCP output shows descriptions never reach the agent, the do not lines move into Code Connect instructions and descriptions serve humans only.

6. **Governance a reviewer can see in the file: the "Component or not" rulings as the entry test and the decision log as the reasoning trail.**
   Reason: GOV.UK admits a component only when it is "Useful" to many teams and "Unique" ([GOV.UK contribution criteria](https://design-system.service.gov.uk/community/contribution-criteria/)). The 2 and 6 Oct rulings already do this job: acted on elements get states, and repetition alone never makes a component. Fourteen design system decisions since 1 Oct carry a "Decided by" line ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). That is rare among public case studies: none of the four individual design system case studies read showed a governance model ([hiring signals notes](../research_notes/Design%20system%20case%20study%20readiness/hiring-signals.md)). A session puts a one board summary of the entry test and the deprecation convention into the library.
   What would change it: if he prefers the case study to show governance from the repo rather than the file, the board is optional and the log stands alone.

7. **Accessibility carried in tokens: a 2 px focus ring width, a 24 px minimum target and each foreground role's description naming the surface it passes contrast on.**
   Reason: WCAG 2.2 sets a 24 by 24 CSS px minimum target at AA and a 2 px, 3:1 focus indicator at AAA ([W3C, What's new in WCAG 2.2](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/)). The input states already use a focus role he set on 30 Sep ([SOURCES](../reference/design-system-cs/SOURCES.md)). Dark only means one set of pairs to check. It takes a day or two and gives reviewers a concrete standard to point at.
   What would change it: if the colour roles turn out to fail contrast on their surfaces, this becomes a fix before it becomes a feature.

8. **Icons: finish moving instances to the published set in wave 1, then either swap TDesign for his own set or name it as a deliberate deferral.**
   Reason: 363 of 440 nested instances in Buttons & chips still point at remote components, 249 of them the TDesign set ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md)). He wanted to "replace the Tdesigns eventually" in Sep 2024 and was working on his own set of 1,000 to 2,000 icons in Sep 2026 ([SOURCES](../reference/design-system-cs/SOURCES.md)). A two year intention closed is a strong before and after; left open, it belongs in the omissions list.
   What would change it: the size of the swap; if it runs past the case study date, record it as in progress.

9. **Defer elevation, motion and component tier tokens, and list them as omissions with reasons.**
   Reason: no source ranks these as what reviewers look for. About half of systems skip component tokens ([zeroheight 2026](https://report.zeroheight.com)). In a dark only interface, depth is usually carried by surface colour steps; that is an inference in the maturity notes, not checked in the file ([maturity signals notes](../research_notes/Design%20system%20case%20study%20readiness/maturity-signals.md)).
   What would change it: if prototypes or handoff start carrying transitions, motion durations become worth a collection.

## What is still unknown

Whether the Figma MCP server passes component descriptions, variable descriptions or code syntax to an agent is undocumented on every Figma page opened; the agent test's raw output before and after the publish answers it ([ai ready systems notes](../research_notes/Design%20system%20case%20study%20readiness/ai-ready-systems.md)). How long Professional keeps version history and whether any "Dev pulled" named versions exist were not checked, so the duplicates stay until that is known ([current state](../research_notes/Design%20system%20case%20study%20readiness/current-state.md); [impact metrics notes](../research_notes/Design%20system%20case%20study%20readiness/impact-metrics.md)). The gap between today's local library and the last published version cannot be read through the API, so the before rests on the assumption that the last publish predates the 14 Oct work. Whether developers have shared component code to map for Code Connect and whether they use Dev Mode at all wait on their answers. Whether he accepted the 17 to 19 Oct token work is not recorded, and neither are the five picks of #177. No opened hiring source speaks to design system case studies specifically, since the most promising ones sit behind Medium blocks or a paywall, so the advice on what reviewers want here is generic portfolio guidance applied to systems ([hiring signals notes](../research_notes/Design%20system%20case%20study%20readiness/hiring-signals.md)). Whether Mondai frames can be shown publicly is open ([GAPS](../reference/design-system-cs/GAPS.md), item 15).
