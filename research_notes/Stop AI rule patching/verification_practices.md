# Verification practices: making AI workflow fixes real rather than cosmetic

Scope: concrete methods for improving an LLM-driven process (prompts, CLAUDE.md / instruction files, multi-step writing workflows) by testing outputs instead of adding rules, plus enforcement mechanisms that beat prose rules. Applied throughout to a non-engineer designer running a multi-session case-study drafting process in Claude Code.

Evidence labels used below: **[Evidence]** = peer-reviewed or empirical study with measured results; **[Vendor practice]** = official Anthropic/OpenAI docs or engineering posts describing what they do internally (experience-based, rarely with published numbers); **[Practitioner opinion]** = individual consultant or blogger guidance.

## Eval-driven development: small test sets, before/after comparisons, blind comparisons, golden examples

### Takeaway
Every credible source converges on the same loop: collect a small set (about 20-50) of real inputs drawn from actual failures, define pass/fail checks for each, run the current setup to get a baseline, change one thing, re-run, and compare. Small sets are enough when the effect is large; the hard part is discipline, not volume.

### Cited Findings
- [Vendor practice] Anthropic recommends starting with "20-50 simple tasks drawn from real failures," warning that waiting for a large suite makes evals harder to build later. Start with the manual checks you already run, and convert user-reported failures into test cases. — [Anthropic, Demystifying evals for AI agents (Jan 2026)](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [Vendor practice] A good eval task is one where two domain experts would independently reach the same pass/fail verdict, and each task should have a reference solution (a golden example) that passes all graders. Test both cases where a behavior should occur and where it should not, to avoid one-sided optimization. — [Anthropic, Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [Vendor practice] Grade the output, not the path: "it's often better to grade what the agent produced, not the path it took." Separate capability evals (start low, give a target) from regression evals (should sit near 100% to catch backsliding). A 0% pass rate across many trials usually means the task or grader is broken. — [Anthropic, Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [Vendor practice] Use pass@k (at least one success in k tries) vs pass^k (all k tries succeed); pass^k matters when consistency is what you need. Run multiple trials because outputs are non-deterministic. — [Anthropic, Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [Vendor practice] Anthropic's research-agent team started with "about 20 queries representing real usage patterns"; small samples sufficed because "a prompt tweak might boost success rates from 30% to 80%." Human testers still caught a failure automation missed (agents favoring "SEO-optimized content farms" over authoritative sources). — [Anthropic, How we built our multi-agent research system (2025)](https://www.anthropic.com/engineering/multi-agent-research-system)
- [Vendor practice] Anthropic's prompt-eval docs: success criteria should be Specific, Measurable, Achievable, Relevant (e.g., "accurate sentiment classification" instead of "good performance"); evals should mirror the real task distribution including edge cases; "more questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals." Use a different model to grade than the one that generated the output when possible. — [Anthropic, Define success criteria and build evaluations](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)
- [Vendor practice] OpenAI: "Adopt eval-driven development: Evaluate early and often"; "Log everything" so you can mine logs for eval cases; grow the eval set from real usage over time. Prefer pairwise comparison or pass/fail for LLM judges over open-ended scoring; control for judge bias toward longer responses and toward position in pairwise comparisons. Named anti-patterns: "vibe-based evals," generic metrics, unrepresentative datasets, uncalibrated automated scores. — [OpenAI, Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
- [Practitioner opinion] Eugene Yan frames evals as the scientific method: observe data, annotate passes and fails (suggests roughly a 50:50 pass/fail sample), hypothesize causes, run an experiment with a baseline/control and pre-stated outcomes that would confirm or reject the hypothesis, then measure (accuracy, defect counts, or pairwise win rates). "An LLM-as-judge won't save the product; fixing your process will." — [Eugene Yan, An LLM-as-Judge Won't Save The Product (Apr 2025)](https://eugeneyan.com/writing/eval-process/)
- [Practitioner opinion] Hamel Husain's three levels: (1) cheap assertion tests run on every change, (2) human and model review of logged traces with binary labels, (3) A/B tests of real outcomes. New failures found in the data are added as tests; the suite grows over time. Prompt changes are checked against Level 1 tests for fast feedback, and one error's prevalence is tracked before and after a fix. — [Hamel Husain, Your AI Product Needs Evals (Mar 2024)](https://hamel.dev/blog/posts/evals/)
- [Practitioner opinion] Hamel discourages writing evaluators before you have observed errors ("eval-driven development" in the strict test-first sense); fix obvious prompt gaps first, and build automated evaluators only for failures that persist. This is a mild contrast with OpenAI's and Yan's "define evals first" framing. — [Hamel Husain, LLM Evals FAQ](https://hamel.dev/blog/posts/evals-faq/); contrasted with [OpenAI](https://developers.openai.com/api/docs/guides/evaluation-best-practices) and [Eugene Yan](https://eugeneyan.com/writing/eval-process/)
- [Practitioner opinion] Retire or run less often an eval that always passes; re-run error analysis after significant changes. — [Hamel Husain, LLM Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)

### Inferences
- For a case-study drafting process, the "test set" can be tiny and concrete: 5-10 saved inputs (e.g., the same project notes/brief fed into a drafting step) plus a short list of binary checks per output ("opens with the user problem, not the solution"; "no unsupported metric claims"; "under N words"; "no banned phrases"). Re-run the same inputs after each change to CLAUDE.md or a skill, and compare against the saved previous outputs. Without this, a "fix" is only a belief.
- Blind comparison is feasible for a solo designer: generate drafts from old and new setups for the same input, strip labels, randomize order, and pick the better one before revealing which is which. OpenAI's position-bias warning applies to human and model judges alike, so swap order.
- A golden example (one finished case study the designer considers excellent) serves both as a reference output for comparison and, per Anthropic's context-engineering advice below, as a better instruction than a list of rules.

### Gaps
- No source gives a validated minimum test-set size for creative/long-form writing tasks; the 20-50 figures come from agent/coding and research contexts.
- I found no published controlled study comparing blind A/B review against unblinded review for prompt iteration specifically; the bias warnings come from LLM-judge literature and vendor guidance.

## Error analysis and root cause: reading failed outputs, categorizing failure modes, fixing the category

### Takeaway
Error analysis means reading many real outputs, writing free-text notes on what went wrong (open coding), grouping notes into a small failure taxonomy (axial coding), counting each category, and fixing the most frequent category at its cause. It is the step practitioners call most important and the one most often skipped in favor of adding another rule.

### Cited Findings
- [Practitioner opinion] Hamel Husain calls error analysis "the most important activity in evals." Process: a domain expert reviews traces and writes free-text notes (open coding; annotate at least ~30 yourself before trusting any AI suggestions), groups notes into a failure taxonomy and counts per category (axial coding, called "the most important step"), and keeps reviewing until new traces stop revealing new failure modes ("theoretical saturation"), suggested ~100 traces. — [Hamel Husain, LLM Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)
- [Practitioner opinion] Do not write a rubric before reviewing outputs; rubrics written in advance can make reviewers miss problems outside the criteria, and "criteria drift" (your sense of good changes as you read) is expected. — [Hamel Husain, LLM Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)
- [Practitioner opinion] Use binary pass/fail per failure mode rather than 1-5 scales; track gradual progress with several specific binary sub-checks; one judge per failure mode, not one judge for "overall quality." Appoint a single "benevolent dictator" domain expert as final quality arbiter. — [Hamel Husain, LLM Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)
- [Practitioner opinion] Hypothesize causes using evidence (inputs, reasoning traces, erroneous outputs), then test each hypothesis with a controlled experiment rather than applying a fix and assuming success. — [Eugene Yan](https://eugeneyan.com/writing/eval-process/)
- [Vendor practice] "Read the transcripts!" to tell whether a failure reflects a real agent mistake or a grader error. — [Anthropic, Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [Vendor practice] Anthropic's research team "watched agents work step-by-step" using the exact prompts and tools, which exposed failure categories (continuing after enough results, wrong tool choice); a tool-testing agent that rewrote flawed tool descriptions cut later task completion time by 40%. — [Anthropic, Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- [Vendor practice] Claude Code best practices: "Address root causes, not symptoms," and if Claude keeps doing something despite a rule, treat that as a signal about the instruction file (too long, rule lost) rather than a reason to add emphasis or more rules. After two failed corrections in a session, clear context and rewrite the initial prompt with what you learned. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [Vendor practice] Anthropic context engineering: start with a bare-bones prompt, then add instructions and examples only to address failure modes that testing reveals. — [Anthropic, Effective context engineering for AI agents (Sep 2025)](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- [Evidence] LLMs locating their own errors is the weak link: in BIG-Bench Mistake, models generally failed to find logical mistakes even in unambiguous cases, but corrected them well once given the mistake's location. Poor self-correction "mainly stems from the mistake-finding step." — [Tyen et al., LLMs cannot find reasoning errors, but can correct them given the error location (ACL Findings 2024)](https://arxiv.org/abs/2311.08516)

### Inferences
- Applied to case-study drafting: after each session, collect the outputs the designer rejected or heavily edited, write one line on each problem, then group them (e.g., "solution-first framing," "invented metrics," "generic AI phrasing," "lost earlier decision after compaction," "ignored stated audience"). Count. Fix the top category with the cheapest mechanism that addresses its cause (a golden example, a deterministic check, a handoff file, a fresh-context reviewer), not by appending a new rule each time an instance appears.
- The Tyen finding implies the human's highest-leverage role is locating problems precisely ("paragraph 3 claims a 40% lift with no source") rather than issuing general corrections; the model is good at fixing once pointed at the spot.
- "Fixing the instance" (adding a rule after one bad draft) is the pattern all these sources warn against; fixing the category requires seeing the category, which requires reading several outputs together.

### Gaps
- Error-analysis literature is almost entirely about production LLM apps with many traces; I found no source adapting open/axial coding specifically to a single person's multi-session writing workflow with only a handful of outputs per week. Thresholds like 30 or 100 traces may be unreachable; saturation (no new failure types appearing) is the more portable stopping rule.

## Deterministic enforcement vs prose: hooks, scripts, checks, schemas

### Takeaway
Anthropic's own docs state that CLAUDE.md instructions are advisory while hooks are deterministic. Any rule that must hold every time and can be checked mechanically (file location, banned words, required sections, word counts, "run the check before stopping") should be code, not text. Judgment-based checks can be enforced at a specific moment with prompt- or agent-based hooks.

### Cited Findings
- [Vendor practice] "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." "Use hooks for actions that must happen every time with zero exceptions." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [Vendor practice] Fix for an over-specified CLAUDE.md: "If Claude already does something correctly without the instruction, delete it or convert it to a hook." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [Vendor practice] "Give Claude a check it can run... Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." Escalating gates: ask in the prompt; a `/goal` condition re-checked by a separate evaluator after every turn; a Stop hook that "runs your check as a script and blocks the turn from ending until it passes"; or a verification subagent so "the agent doing the work isn't the one grading it." Have Claude show evidence (command output, screenshot) rather than assert success. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [Vendor practice] Hooks are shell commands run at lifecycle points "rather than relying on the LLM to choose to run them." Events include SessionStart, UserPromptSubmit, PreToolUse (can block a tool call), PostToolUse, Stop, SubagentStop, among others. A hook exiting with code 2 blocks the action and (for most events) feeds stderr back to Claude as feedback so it can adjust; e.g., a PreToolUse script blocking edits to protected files. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- [Vendor practice] A SessionStart hook with a `compact` matcher can re-inject critical context after every compaction, addressing lost details in long sessions. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- [Vendor practice] Prompt-based hooks (`type: "prompt"`) send the hook input to a Claude model that returns `{"ok": true/false, "reason": ...}`; on a Stop hook, `ok:false` feeds the reason back so Claude keeps working. Agent-based hooks (`type: "agent"`, experimental) spawn a subagent with tool access (up to 50 turns) to verify against actual file state before allowing a stop. Stop hooks should check `stop_hook_active` to avoid infinite loops; Claude Code overrides a Stop hook after eight consecutive blocks. — [Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)
- [Practitioner opinion] Code assertions before LLM judges: use code when a deterministic rule can catch the failure; use an LLM judge only for failures that need human-like judgment. — [Hamel Husain, LLM Evals FAQ](https://hamel.dev/blog/posts/evals-faq/); same ordering in [Anthropic, Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) ("deterministic graders where possible, LLM graders where necessary")
- [Practitioner opinion] Don't use CLAUDE.md as a linter: style rules bloat context and reduce instruction-following; use Stop hooks, auto-fixing linters, or slash commands instead. — [HumanLayer, Writing a good CLAUDE.md (Nov 2025)](https://www.humanlayer.dev/blog/writing-a-good-claude-md)
- [Vendor practice] Brittle hardcoded if-else logic in prompts creates fragility and maintenance cost; the alternative is the "right altitude" (specific heuristics, not exhaustive rules). — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- [Vendor practice] Agents should get "ground truth" from the environment at each step (tool results, code execution) to assess progress. — [Anthropic, Building effective agents (Dec 2024)](https://www.anthropic.com/engineering/building-effective-agents)

### Inferences
- Rule of thumb for deciding code vs text: if you could write the check as "does the file contain X / exceed N words / live in folder Y / include section Z," it belongs in a script or hook. If it needs judgment ("is the narrative user-first?"), it belongs in a separate reviewer (prompt/agent Stop hook or subagent) with a narrow binary question, not in an ever-growing CLAUDE.md.
- Concrete examples for case-study drafting: a script that greps a draft for a banned-phrase list and fails with the offending lines; a word-count/section-presence check run by a Stop hook; a PreToolUse hook blocking writes to a "final/approved" folder; a SessionStart(compact) hook that re-injects the project's decision log so later sessions don't lose earlier decisions. Claude can write these hooks if asked ("write a hook that..."), which matters for a non-engineer.
- A hook only enforces what it checks. A passing Stop hook proves the mechanical criteria, not overall quality, so it complements rather than replaces reading outputs.

### Gaps
- I found no controlled study quantifying adherence rates of prose rules vs hooks in Claude Code; the "advisory vs deterministic" distinction is architectural (hooks run outside the model) and stated by Anthropic, not measured.
- Agent-based hooks are labeled experimental; reliability for judgment-heavy writing checks is undocumented.

## Independent reviewer/critic agents and generator-verifier separation: effectiveness and limits

### Takeaway
Research is consistent that a model asked to critique itself, with no external signal, does not reliably improve and can get worse; gains come from external feedback (tests, tools, ground truth, humans) or a well-specified separate check. Fresh-context reviewers help, but they are biased toward finding something, may favor outputs from their own model family, and must be given narrow criteria.

### Cited Findings
- [Evidence] "Large Language Models Cannot Self-Correct Reasoning Yet": without external feedback, models struggle to fix their own reasoning answers and performance sometimes drops after self-correction; earlier positive results often relied on oracle labels or weak initial prompts. Multi-agent debate did not beat self-consistency at equal numbers of responses. — [Huang et al., ICLR 2024](https://arxiv.org/abs/2310.01798v2)
- [Evidence] Critical survey: no prior work shows successful self-correction using feedback from prompted LLMs except in tasks exceptionally suited to it; self-correction works well when reliable external feedback is available (e.g., code execution) and with large-scale fine-tuning. Many prior studies over-evaluate self-correction. — [Kamoi et al., TACL 2024](https://aclanthology.org/2024.tacl-1.78/)
- [Evidence] Error-finding, not error-fixing, is the bottleneck: models fail to locate mistakes but fix them when given location; a small trained classifier beat prompting a large model at mistake-finding. — [Tyen et al., ACL Findings 2024](https://arxiv.org/abs/2311.08516)
- [Evidence] Self-preference bias: LLM evaluators score their own outputs higher than others' that humans rate equal; GPT-4 recognized its own text with ~73.5% accuracy, and self-recognition strength correlated linearly with self-preference (causal via fine-tuning). Main experiments on summarization, so generality is less established. — [Panickssery, Bowman & Feng, NeurIPS 2024](https://arxiv.org/pdf/2404.13076)
- [Vendor practice] Anthropic recommends a different model grade than the one that generated output, when possible. — [Anthropic, develop tests](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)
- [Vendor practice] Writer/Reviewer pattern: "A fresh context improves code review since Claude won't be biased toward code it just wrote." A reviewer subagent "sees only the diff and the criteria you give it, not the reasoning that produced the change." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [Vendor practice] Limit: "A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do. Chasing every finding leads to over-engineering." Tell the reviewer to flag only gaps affecting correctness or stated requirements. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [Vendor practice] Evaluator-optimizer workflow (one LLM generates, another evaluates in a loop) fits when there are clear evaluation criteria and iterative refinement provides measurable value; signs of fit are that human feedback demonstrably improves the output and an LLM can provide similar feedback. — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- [Vendor practice] LLM judges "should be closely calibrated with human experts"; give them an "Unknown" option and grade each rubric dimension with a separate judge. Anthropic's research system found a single LLM call outputting 0.0-1.0 scores plus pass/fail most consistent with human judgment for its use case. — [Anthropic, Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [Anthropic, Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- [Practitioner opinion] Validate a judge before trusting it: label ~100-200 examples per failure mode, measure true positive rate and true negative rate separately (raw agreement misleads with imbalanced classes). — [Hamel Husain, LLM Evals FAQ](https://hamel.dev/blog/posts/evals-faq/); [Hamel Husain, Your AI Product Needs Evals](https://hamel.dev/blog/posts/evals/)
- [Practitioner opinion] Calibrate LLM judges against human annotations (precision/recall); they scale monitoring but don't replace human sampling. — [Eugene Yan](https://eugeneyan.com/writing/eval-process/); [OpenAI](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

### Inferences
- Asking the same drafting session to "review your draft against the rules" is the weakest form of verification the evidence describes. Better, in order: deterministic checks; a fresh-context reviewer with a short, binary, specific checklist and no access to the drafting reasoning; the designer's own blind read. Each reviewer criterion should name what counts as a failure, otherwise the reviewer manufactures findings.
- For a solo designer, judge validation can be scaled down: on 10-20 past drafts the designer has already judged, check whether the reviewer agent's pass/fail matches. If it disagrees often, the reviewer prompt (not the drafting prompt) needs work, and its output shouldn't gate anything yet.
- Self-preference bias means a Claude reviewer of Claude drafts may be lenient on "AI-sounding" qualities; the designer's own judgment remains the reference standard (Hamel's "benevolent dictator").

### Gaps
- Most self-correction evidence is on reasoning/math/QA tasks; I found no rigorous study of separate-critic effectiveness for long-form persuasive or narrative writing like case studies.
- No published numbers on how much Claude Code's fresh-context reviewer subagent improves outcomes; the guidance is experience-based.

## Pruning instruction files: evidence that removing or consolidating rules improves adherence

### Takeaway
Measured evidence shows instruction-following degrades as the number of simultaneous instructions grows, with a bias toward earlier instructions, and Anthropic's own docs say bloated CLAUDE.md files cause Claude to ignore instructions. The prescribed fix is to cut any line whose removal wouldn't cause mistakes, move situational guidance into on-demand skills, move mechanical rules into hooks, and test that behavior actually changes.

### Cited Findings
- [Evidence] IFScale benchmark (500 keyword-inclusion instructions in a business-report writing task, 20 models): even the best frontier models reached only ~68% accuracy at 500 instructions. Three degradation patterns: threshold decay (reasoning models such as o3, Gemini 2.5 Pro), linear decay (GPT-4.1, Claude Sonnet 4), exponential decay (GPT-4o, Llama 4 Scout). Models show bias toward earlier instructions. Caveat: instructions were simple keyword inclusions, not the nuanced style rules typical of CLAUDE.md. — [Distyl AI, How Many Instructions Can LLMs Follow at Once? (arXiv 2507.11538, NeurIPS 2025)](https://arxiv.org/abs/2507.11538)
- [Vendor practice] "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" For each line ask, "Would removing this cause Claude to make mistakes?" If not, cut it. "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." "Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [Vendor practice] Emphasis inflation: "If you emphasize many lines, none of them stands out." Add emphasis such as IMPORTANT to a single repeatedly skipped line only. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [Vendor practice] CLAUDE.md loads every session, so include only broadly applicable content; use skills for knowledge or workflows only sometimes relevant, since they load on demand. Exclude self-evident practices, long explanations, and frequently changing information. — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [Vendor practice] Context is finite with diminishing returns; recall degrades as context grows ("context rot"). Aim for "the minimal set of information that fully outlines your expected behavior" (minimal is not necessarily short). Prefer a small set of diverse canonical examples over a "laundry list of edge cases": "examples are the 'pictures' worth a thousand words." — [Anthropic, Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- [Vendor practice] Performance degrades as the context window fills; Claude may "forget" earlier instructions. A clean session with a better prompt "almost always outperforms a long session with accumulated corrections." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- [Practitioner opinion, partly cited] HumanLayer cites IFScale for a claim that frontier thinking models follow ~150-200 instructions with reasonable consistency (the author notes this "hasn't been investigated in an incredibly rigorous manner"); the author's own count is ~50 instructions in Claude Code's system prompt before any user file loads, and reports Claude Code wraps CLAUDE.md with a reminder that it "may or may not be relevant." Recommends under ~300 lines (author's file is under 60), progressive disclosure via separate files, and not using CLAUDE.md for style linting. The 150-200 figure is the blogger's reading of the paper, not a number the paper states as a threshold. — [HumanLayer, Writing a good CLAUDE.md (Nov 2025)](https://www.humanlayer.dev/blog/writing-a-good-claude-md)

### Inferences
- Each rule added after a single bad output has a cost to every other rule. Instruction files that grow by patching drift toward the regime where adherence degrades, which is consistent with the "I added a rule and it still happens" experience.
- A pruning pass can be tested like any other change: run the saved case-study inputs with the current file and with the pruned file, compare outputs on the same binary checks. If the pruned version holds or improves, the removed lines weren't doing work.
- For the case-study process: one golden finished case study plus a few short principles likely outperforms a long list of "never do X" rules; mechanical "never" rules move to a check script; stage-specific guidance (intake vs drafting vs polish) moves into separate skills loaded only at that stage.

### Gaps
- No controlled study found that directly measures adherence before vs after pruning a real CLAUDE.md; the evidence is (a) IFScale on synthetic simple instructions and (b) Anthropic's experience-based guidance.
- The ~150-200 instruction "capacity" and the 300-line guideline are practitioner heuristics; treat them as rough, not thresholds.
