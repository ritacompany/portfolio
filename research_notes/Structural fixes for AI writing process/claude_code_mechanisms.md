# Claude Code mechanisms that enforce a multi-step process structurally

Context for the report writer: the target is a 7-step case study loop (open, talk, draft, voice pass, layout, review, save) where sessions skip steps, grade their own work and accumulate about 84 hard-rule lines across 6 files. All docs below were fetched October 2026 from code.claude.com (current Claude Code docs) and anthropic.com/engineering.

## 1. Custom subagents: separating the drafter from the reviewer

### Takeaway
A custom subagent is a Markdown file in `.claude/agents/` with YAML frontmatter; it runs in its own context window, sees only the delegation message Claude writes (not the conversation, not the files already read, not the author's reasoning) and can be pinned to a different model and a read-only tool set. That makes a structurally separate reviewer straightforward; the remaining risk is what the main session puts in the delegation message.

### Cited Findings
- Only `name` and `description` are required. Other frontmatter fields: `tools`, `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `skills`, `mcpServers`, `hooks`, `memory`, `background`, `omitClaudeMd`, `effort`, `isolation`, `color`, `initialPrompt`. Unrecognized fields "are ignored without an error". Source: [Subagents docs](https://code.claude.com/docs/en/sub-agents)
- `tools`: "Tools the subagent can use, as a comma-separated string such as `Read, Grep, Bash` or a YAML list. Inherits every tool available to subagents if omitted." `disallowedTools`: "Tools to deny, removed from inherited or specified list." Source: [Subagents docs](https://code.claude.com/docs/en/sub-agents)
- `model` accepts "`sonnet`, `opus`, `haiku`, `fable`, a full model ID such as `claude-opus-5-5`, or `inherit`". Resolution order: per-invocation `model` parameter, then the definition's `model` frontmatter, then `CLAUDE_CODE_SUBAGENT_MODEL`, then the main conversation's model. Source: [Subagents docs](https://code.claude.com/docs/en/sub-agents)
- Isolation: a subagent "doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read. Claude composes a delegation message that summarizes the task, and the subagent works from there." Its initial context is its own system prompt plus environment details (not the Claude Code system prompt), the task message, CLAUDE.md files (unless `omitClaudeMd: true`), a git status snapshot, preloaded `skills`, and a sibling roster. Output styles and auto memory do not reach non-fork subagents. A "fork" is the exception: it "inherits the entire conversation so far instead of starting fresh." Source: [Subagents docs](https://code.claude.com/docs/en/sub-agents)
- `skills` frontmatter preloads full skill content into the subagent: "The full skill content is injected, not only the description." Source: [Subagents docs](https://code.claude.com/docs/en/sub-agents)
- File locations and priority: managed settings (1), `--agents` CLI flag (2), `.claude/agents/` (3), `~/.claude/agents/` (4), plugin `agents/` (5). Directories are watched so edits usually apply without a restart. Source: [Subagents docs](https://code.claude.com/docs/en/sub-agents)
- Explicit invocation: natural language ("Use the test-runner subagent..."), @-mention `@"code-reviewer (agent)"`, or session-wide `claude --agent code-reviewer` / `"agent": "code-reviewer"` in `.claude/settings.json`. Subagents can nest up to three layers; `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` turns nesting off. Source: [Subagents docs](https://code.claude.com/docs/en/sub-agents)
- Anthropic's own framing of the reviewer pattern: "A reviewer running in a fresh subagent context sees only the diff and the criteria you give it, not the reasoning that produced the change, so it evaluates the result on its own terms." Source: [Best practices](https://code.claude.com/docs/en/best-practices)
- Anthropic's caveat on reviewers: "A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do. Chasing every finding leads to over-engineering... Tell the reviewer to flag only gaps that affect correctness or the stated requirements, and treat the rest as optional." Source: [Best practices](https://code.claude.com/docs/en/best-practices)
- Writer/Reviewer across separate sessions: "A fresh context improves code review since Claude won't be biased toward code it just wrote." Source: [Best practices](https://code.claude.com/docs/en/best-practices)
- Four escalating ways to gate "done": in one prompt; a `/goal` condition where "A separate evaluator re-checks it after every turn"; "a Stop hook runs your check as a script and blocks the turn from ending until it passes"; and "a verification subagent or a dynamic workflow... so the agent doing the work isn't the one grading it." Source: [Best practices](https://code.claude.com/docs/en/best-practices)
- Example reviewer definition in the docs uses `tools: Read, Grep, Glob, Bash` and `model: opus`; another uses `tools: Read, Glob, Grep` and `model: sonnet`. Source: [Best practices](https://code.claude.com/docs/en/best-practices); [Subagents docs](https://code.claude.com/docs/en/sub-agents)
- Skills can also run as a forked subagent: `context: fork` plus `agent: <type>`; "The subagent doesn't see your conversation history, so the skill's instructions have to stand on their own." Source: [Skills docs](https://code.claude.com/docs/en/skills)

### Inferences
- A `voice-reviewer` or `case-study-reviewer` agent with `tools: Read, Grep, Glob, Write` (Write only so it can save its report file), `model:` set to a different model than the drafting session, and `omitClaudeMd: true` would get a genuinely clean context. Giving it the rubric through its own system prompt or a preloaded `skills:` entry means the rubric lives in one place and is not diluted by the 84 always-loaded lines.
- The leak path is the delegation message: the main session writes it and could include its own justification. Mitigation: have the reviewer read the draft file path and rubric itself, and keep the delegation prompt fixed (for example from a skill or workflow script) rather than composed freely.
- A reviewer with `Write` scoped by a `PreToolUse` hook to only `reviews/*.md` keeps it from editing the draft.

### Gaps
- No doc states a hard guarantee that the main session cannot paraphrase its reasoning into the delegation prompt; isolation is of conversation history, not of what Claude chooses to pass.

## 2. Hooks that block or inject

### Takeaway
Hooks are the deterministic layer: `PreToolUse` can deny a write (exit 2 or `permissionDecision: "deny"`), `Stop`/`SubagentStop` can refuse to end a turn (`decision: "block"` with `reason`), and `UserPromptSubmit`/`SessionStart` can inject state as context. Prompt and agent hook types let a model judge a condition, but command hooks reading files are the only fully deterministic gate.

### Cited Findings
- Docs framing: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." "Use hooks for actions that must happen every time with zero exceptions." Source: [Best practices](https://code.claude.com/docs/en/best-practices)
- Full event list: `SessionStart`, `Setup`, `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `PermissionDenied`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Notification`, `MessageDisplay`, `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `Stop`, `StopFailure`, `TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove`, `PreCompact`, `PostCompact`, `PreModelSwitch`, `PostModelSwitch`, `Elicitation`, `ElicitationResult`, `SessionEnd`. Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- Exit code 2 blocks on: `PreToolUse` (blocks the tool call), `UserPromptSubmit` (blocks the prompt), `Stop` ("Prevents Claude from stopping and continues the conversation"), `SubagentStop`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`, `PostToolBatch`, `PreCompact`, `ConfigChange` and others. Exit 2 does not block on `PostToolUse`, `SessionStart`, `SubagentStart`, `InstructionsLoaded`, `Notification` and others. Exit 0 parses stdout as JSON; other non-zero codes are non-blocking errors. Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- JSON decision fields: top-level `"decision": "block"` plus `reason` for `UserPromptSubmit`, `PostToolUse`, `PostToolBatch`, `Stop`, `SubagentStop`, `PreCompact`, `ConfigChange`; for `PreToolUse` it is `hookSpecificOutput.permissionDecision` (`allow`/`deny`/`ask`/`defer`) with `permissionDecisionReason`. Universal `continue: false` stops Claude and takes precedence; `stopReason` is shown to the user. Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- `PreToolUse` input for Write: `tool_input.file_path` (always absolute) and `content`; for Edit: `file_path`, `old_string`, `new_string`, `replace_all`. Common fields: `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`. Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- `PreToolUse` deny beats permission mode: "A hook that returns `permissionDecision: "deny"` blocks the tool even in `bypassPermissions` mode or with `--dangerously-skip-permissions`." A hook returning allow cannot bypass settings deny rules. Source: [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Docs' protected-files example: a `PreToolUse` hook with `"matcher": "Edit|Write"` runs `protect-files.sh`, which reads `.tool_input.file_path` with jq and does `echo "Blocked: ..." >&2; exit 2`; "Claude receives feedback explaining why the edit was blocked, so it can adjust its approach." Source: [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- `if` field narrows a handler using permission-rule syntax, e.g. `"if": "Edit(*.ts)"` or `"Bash(git *)"`; only works on tool events. The guide warns the Bash filter is best-effort: "use the permission system rather than a hook to enforce a hard allow or deny." Source: [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- `Stop`/`SubagentStop` input includes `stop_hook_active` ("`true` when Claude Code is already continuing as a result of a stop hook") and `last_assistant_message`. SubagentStop adds `agent_id`, `agent_type` (the matcher value) and `agent_transcript_path`. `decision: "block"` "prevents Claude from stopping"; `reason` is required and "Tells Claude why it should continue." On SubagentStop, block "keeps the subagent running and delivers `reason` to the subagent as its next instruction." Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- Loop guard: "after stop hooks have continued the turn eight times in a row, Claude Code overrides the next block and ends the turn. The count of consecutive continuations resets each time Claude calls a tool. To raise the cap, set `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`." The guide's recommended script start: `if [ "$(echo "$INPUT" | jq -r '.stop_hook_active')" = "true" ]; then exit 0; fi`. Source: [Hooks reference](https://code.claude.com/docs/en/hooks); [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- `Stop` fires "whenever Claude finishes responding, not only at task completion. They don't fire on user interrupts." Source: [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- `UserPromptSubmit` cannot rewrite the prompt; it injects `additionalContext` (or plain stdout on exit 0) "as a system reminder". Docs advise phrasing injected context "as factual statements, not imperative instructions, or Claude's prompt-injection defenses may surface it to the user instead." Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- `PostToolUse` "can't undo actions since the tool has already executed"; `decision: "block"` only adds `reason` next to the tool result. Source: [Hooks guide](https://code.claude.com/docs/en/hooks-guide); [Hooks reference](https://code.claude.com/docs/en/hooks)
- Prompt hooks (`type: "prompt"`) send the hook input plus your prompt to a model, which returns `{"ok": true|false, "reason": "...", "impossible": true|false}`. On `Stop`/`SubagentStop`, `ok: false` feeds the reason back as the next instruction unless `impossible: true`. On `PreToolUse`, `ok: false` denies and by default ends the turn unless `continueOnBlock: true`. Optional `model` field. Agent hooks (`type: "agent"`) spawn a verifier with Read/Grep/Glob for up to 50 turns; marked "experimental... For production workflows, prefer command hooks." Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- Timeouts: `command`, `http`, `mcp_tool` default 600 seconds, lowered to 30 seconds on `UserPromptSubmit`; `prompt` 30 seconds; `agent` 60 seconds. "A timed-out `command` or `http` hook on `PreToolUse` doesn't block the call unless `onFailure: "block"` is set." On a `UserPromptSubmit` timeout the output "including any `additionalContext`, is discarded." Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- Multiple matching hooks run in parallel; for `PreToolUse` "the most restrictive answer applies, in the order `deny`, `defer`, `ask`, `allow`." Source: [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Hooks can live in `.claude/settings.json` (shareable), `.claude/settings.local.json`, `~/.claude/settings.json`, plugins, skill frontmatter (registered for the rest of the session once invoked; `once: true` removes after first success) and subagent frontmatter (only while that subagent runs; "Claude Code converts a `Stop` hook here to `SubagentStop`"). Project subagent frontmatter hooks run only after accepting workspace trust. Source: [Hooks guide](https://code.claude.com/docs/en/hooks-guide); [Hooks reference](https://code.claude.com/docs/en/hooks)
- Gotcha: shell profile output before the JSON makes Claude Code read stdout as plain text, so the JSON decision is silently ignored with no visible error; check with `claude --debug` for `Hook output does not start with {`. Source: [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- `"disableAllHooks": true` turns hooks off; project settings can override user settings on this. Source: [Hooks guide](https://code.claude.com/docs/en/hooks-guide)

### Inferences
- "Block a write that marks a section built unless a reviewer report exists": a `PreToolUse` hook on `Edit|Write` matched to the status file, which parses `tool_input.content` (Write) or `new_string` (Edit) for a transition to `built`, then checks for `reviews/<section>-review.md` newer than the draft and exits 2 with a stderr reason if missing. Deterministic, and survives any permission mode.
- A `Stop` hook is the place for "you cannot end the turn mid-step", but because Stop fires on every reply, including normal conversation in the "talk" step, it must read the state file and only block when the state says a step is open and its artifact is missing. Always exit early on `stop_hook_active`. The 8-block cap means it is a strong nudge, not a wall.
- A `SubagentStop` hook matched to the reviewer's `agent_type` can refuse to let the reviewer finish until its report file exists in the expected format.
- A `UserPromptSubmit` or `SessionStart` hook can print the current step and its single next action from the state file, replacing prose "start by reading X" rules. Phrase it as facts ("Current step: voice pass. Required artifact: ... missing.").
- Use prompt hooks sparingly: they reintroduce model judgment, which is the problem being fixed. Keep checkable gates as command hooks.

### Gaps
- No size cap for `additionalContext` was found in the docs fetched.

## 3. Encoding the pipeline as a state machine

### Takeaway
Anthropic's long-running-agent harness is the closest published pattern: a JSON state file the agent may only flip specific fields on, plus a progress log and git, read at the start of every session. Claude Code adds the enforcement half: hooks that read the state file and reject illegal transitions. No canonical open-source "hook state machine" project was found; teams compose it from these primitives.

### Cited Findings
- "Effective harnesses for long-running agents" (Justin Young, Anthropic, Nov 26 2025): an initializer agent creates `init.sh`, a progress log `claude-progress.txt`, an initial git commit and a feature list where each entry has a category, description, test steps and a `passes` field; "Coding agents change only the `passes` status." Source: [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Why JSON: "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files." Source: [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Failure modes it names map to the portfolio problem: declaring victory early after seeing partial progress, and "marking features done without testing"; fixes were a complete feature list read at session start and self-verification before marking passing. Working one feature at a time was called "critical". Source: [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Session start routine: check working directory, read git log and progress notes, choose a feature, run init.sh, do a basic end-to-end check. Source: [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Prompt chaining with "programmatic checks (see "gate" in the diagram below) on any intermediate steps" is Anthropic's named pattern for fixed sequential steps. Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Structured note-taking: "the agent regularly writes notes persisted to memory outside of the context window", e.g. "maintaining a NOTES.md file". Source: [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Community: no dedicated GitHub project implementing a hook state machine surfaced; a skill registry lists a "global-hook-setup" skill claiming hooks for "state transitions", and the anthropics/claude-code "Hook Development" skill lists "Enforce completion standards (Stop, SubagentStop)". Neither was verified in code. Source: [skills.sh Hook Development](https://skills.sh/anthropics/claude-code/hook-development); [openskillindex global-hook-setup](https://openskillindex.com/skills/majiayu000-claude-skill-registry-global-hook-setup)
- TDD Guard is a working example of hook-enforced process: "When your agent tries to skip tests or over-implement, TDD Guard blocks the action and explains what needs to happen instead"; it uses a configurable validation model. Its README does not document which events it uses. Source: [nizos/tdd-guard](https://github.com/nizos/tdd-guard)
- `TaskCreated`/`TaskCompleted` hooks can block task creation or completion (exit 2 "Prevents the task from being marked complete"), so the built-in task list can also act as a gated checklist. Source: [Hooks reference](https://code.claude.com/docs/en/hooks)
- Dynamic workflows move the plan into code: "A workflow moves the plan into code... A workflow script holds the loop, the branching, and the intermediate results itself." Scripts are JS saved to `.claude/workflows/` with `export const meta = { name, description }`, `agent()`, `pipeline()`, `parallel()`, `phase()`, `log()`, an `args` global and optional `schema` for JSON output. Constraint: "No mid-run user input... For sign-off between stages, run each stage as its own workflow." Source: [Workflows docs](https://code.claude.com/docs/en/workflows)

### Inferences
- Suggested shape for the portfolio: a `state/cs2.json` with one entry per section and a `step` enum (`open`, `talk`, `draft`, `voice`, `layout`, `review`, `save`) plus required artifact paths per step. A `PreToolUse` hook on writes to that file allows only the next legal transition and only when the current step's artifact exists. Prose in the process doc then describes intent, not enforcement.
- Workflows fit the non-interactive stretch (draft, voice pass, independent review, report) but not the "talk" step, since there is no mid-run user input. Each human sign-off point should be a workflow boundary.
- Keeping the state file JSON and letting the session touch only the `step` field follows Anthropic's finding that models overwrite Markdown more readily.

### Gaps
- No published Anthropic example of a hook that validates state-file transitions; this is a composition of documented primitives, not a documented recipe.

## 4. Keeping the always-loaded context small

### Takeaway
Anthropic's docs say CLAUDE.md is advisory context, should stay under 200 lines per file, and that bloat makes Claude ignore rules; the fix is to prune, convert checkable rules to hooks, and move situational guidance into skills or path-scoped rules that load on demand.

### Cited Findings
- "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead. The more specific and concise your instructions, the more consistently Claude follows them." Source: [Memory docs](https://code.claude.com/docs/en/memory)
- "Size: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Imports "help you organize a long file but don't reduce its context cost, because imported files also load at launch." Source: [Memory docs](https://code.claude.com/docs/en/memory)
- "CLAUDE.md content is delivered as a user message after the system prompt... there's no guarantee of strict compliance, especially for vague or conflicting instructions." "If two instructions contradict each other, Claude may pick one arbitrarily." Source: [Memory docs](https://code.claude.com/docs/en/memory)
- "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" and "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." Source: [Best practices](https://code.claude.com/docs/en/best-practices)
- On emphasis: "If you emphasize many lines, none of them stands out." Source: [Best practices](https://code.claude.com/docs/en/best-practices)
- Failure pattern "The over-specified CLAUDE.md... Fix: Ruthlessly prune. If Claude already does something correctly without the instruction, delete it or convert it to a hook." Source: [Best practices](https://code.claude.com/docs/en/best-practices)
- Path-scoped rules: `.claude/rules/*.md` with `paths:` frontmatter (glob list) load only "when Claude uses the Read, Write, or Edit tool on a matching file"; rules without `paths` load unconditionally. Nested CLAUDE.md in subdirectories load on demand when Claude touches a file there. Source: [Memory docs](https://code.claude.com/docs/en/memory)
- Block-level HTML comments in CLAUDE.md are stripped before injection, so maintainer notes cost no tokens. `/doctor prompt-audit` reports outdated or conflicting instructions. The `InstructionsLoaded` hook logs which files loaded and why. Source: [Memory docs](https://code.claude.com/docs/en/memory)
- Skills: "Unlike CLAUDE.md content, a skill's body loads only when it's used." Default: description always in context, body on invoke; `disable-model-invocation: true` keeps even the description out of context. Combined `description` and `when_to_use` is truncated at 1,536 characters in the listing. "Keep `SKILL.md` under 500 lines." Supporting files load when SKILL.md points to them. Source: [Skills docs](https://code.claude.com/docs/en/skills)
- Skill frontmatter fields: `name`, `description`, `when_to_use`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context`, `agent`, `background`, `hooks`, `paths`. Slash commands were merged into skills: `.claude/commands/deploy.md` and `.claude/skills/deploy/SKILL.md` both create `/deploy`. `` !`command` `` injects live command output before the skill reaches Claude, and "A failed command aborts the entire skill invocation." Source: [Skills docs](https://code.claude.com/docs/en/skills)
- Output styles are also advisory: "It's an instruction Claude follows, so nothing enforces it." They apply to the main conversation and forks, not to other subagents. `keep-coding-instructions: false` (default for custom styles) drops Claude Code's software-engineering section from the system prompt. Source: [Output styles docs](https://code.claude.com/docs/en/output-styles)
- Context engineering: aim for "the smallest possible set of high-signal tokens"; context rot means recall "decreases" as context grows; avoid "hardcoding complex, brittle logic in their prompts". Sub-agents return "a condensed, distilled summary of its work (often 1,000-2,000 tokens)." (Rajasekaran et al., Sep 29 2025) Source: [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Permission rules give another non-prose control: evaluated "deny, then ask, then allow"; file rules use `Edit(path)` and `Read(path)` with gitignore syntax (`//abs`, `~/`, `/relative-to-settings`, `./`); a `Write(path)` rule "is accepted but never consulted". "A hook that exits with code 2 stops the tool call before permission rules are evaluated." Source: [Permissions docs](https://code.claude.com/docs/en/permissions)
- Plan mode separates read-only exploration from edits (`claude --permission-mode plan`); subagents can be pinned with `permissionMode: plan`. Docs note plan mode "adds overhead" and suit uncertain multi-file work. Source: [Best practices](https://code.claude.com/docs/en/best-practices); [Subagents docs](https://code.claude.com/docs/en/sub-agents)

### Inferences
- Sorting the 84 rule lines into three bins is the direct application: (a) mechanically checkable (em dashes, Oxford commas, "no quotes in CS2", banned names, verbatim-file protection) go to hook scripts; (b) step-specific guidance (voice, layout, review rubric) goes to skills or a reviewer agent's own prompt, loaded only in that step; (c) the few judgment rules that apply every turn stay in CLAUDE.md.
- `paths:`-scoped rules fit the repo layout: e.g. a rule file scoped to `reference/cs2/draft/**` loads only when a CS2 draft is touched.

### Gaps
- Anthropic gives a line target (under 200 per file) but no published number for a total "instruction budget" across all loaded files.

## 5. Anthropic patterns: evaluator-optimizer, orchestrator-workers, harnesses

### Takeaway
Anthropic distinguishes fixed workflows (code decides the path) from agents (model decides), and recommends the simplest structure that works; for a known 7-step process that is prompt chaining with programmatic gates plus an evaluator-optimizer loop for the review step.

### Cited Findings
- "Workflows are systems where LLMs and tools are orchestrated through predefined code paths." Agents: "LLMs dynamically direct their own processes and tool usage." (Erik S. and Barry Zhang, Dec 19 2024; page notes tooling has changed since) Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Prompt chaining "decomposes a task into a sequence of steps, where each LLM call processes the output of the previous one," with programmatic gates. Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Orchestrator-workers: "a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results"; subtasks are decided at runtime. Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Evaluator-optimizer: "one LLM call generates a response while another provides evaluation and feedback in a loop," best when there are clear evaluation criteria. Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- "We recommend finding the simplest solution possible, and only increasing complexity when needed." Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Claude Code's own table: with subagents and skills "Claude, turn by turn" decides what runs next; with workflows "The script" decides. Workflows can "have independent agents adversarially review each other's findings before they're reported." Source: [Workflows docs](https://code.claude.com/docs/en/workflows)
- Best practices: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." Source: [Best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- The portfolio loop is a predefined path, so the "workflow" end of Anthropic's spectrum applies: the order is fixed by hooks and state, not left to the session. The review step is an evaluator-optimizer loop where the evaluator is a separate subagent with its own rubric and, optionally, a different model.
- "Talk" and final approval are human gates; Claude Code has no mechanism that substitutes for them, and workflows explicitly cannot pause for input mid-run.

### Gaps
- No Anthropic post specifically addresses writing (non-code) pipelines; the patterns are general and transfer by analogy.
