# Skills, plugins and marketplaces for critique, evaluation and long-form writing

All star counts and last-push dates below were read from the GitHub REST API on 2026-10-10 (pushed_at = last push to any branch, the closest available proxy for last commit). Nothing was installed. Repo existence is confirmed for every repo with a star count; anything without one is marked unverified.

## Official: Anthropic skills repo, the plugin marketplace and official plugins. Which patterns transfer to writing?

### Takeaway
The transferable patterns are mechanical, not textual: parallel independent reviewers plus a separate confidence scorer with a hard cutoff (code-review), declarative regex rules that block or warn at tool-use or Stop time (hookify) and a context-free reader subagent that must answer questions from the document alone (doc-coauthoring). Each of these moves judgment out of the drafting session, which is the exact failure described (self-judging, skipped steps).

### Cited Findings
- anthropics/skills: 180,319 stars, last push 2026-10-09, org-owned by `anthropics`; GitHub licence field empty because licensing is per skill. Many skills are Apache 2.0; the document skills (docx, pdf, pptx, xlsx) are source-available, not open source. Skill format is a folder with `SKILL.md` and YAML frontmatter, only `name` and `description` required. [GitHub API](https://api.github.com/repos/anthropics/skills); [README](https://github.com/anthropics/skills)
- doc-coauthoring skill: three stages, Context Gathering (5 to 10 clarifying questions), Refinement and Structure (section by section, brainstorm 5 to 20 options, user curates, Claude drafts) and Reader Testing. In Reader Testing, Claude predicts 5 to 10 reader questions and sends each to a sub-agent that receives only the document and the question, then checks ambiguity, false assumptions and contradictions; loops until the fresh reader answers correctly. No scripts, no network calls of its own. [SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/doc-coauthoring/SKILL.md)
- Official plugins live in anthropics/claude-code `plugins/`: agent-sdk-dev, claude-opus-4-5-migration, code-review, commit-commands, explanatory-output-style, feature-dev, frontend-design, hookify, learning-output-style, plugin-dev, pr-review-toolkit, ralph-wiggum, security-guidance. Plugin structure: `.claude-plugin/plugin.json`, optional `commands/`, `agents/`, `skills/`, `hooks/`, `.mcp.json`. [plugins dir](https://github.com/anthropics/claude-code/tree/main/plugins)
- code-review: `/code-review` launches 4 parallel agents. Agents 1 and 2 both check CLAUDE.md compliance (deliberate redundancy), agent 3 scans for obvious bugs in changed code only, agent 4 uses git blame and history. Each issue is then scored independently by its own scorer on 0/25/50/75/100; for CLAUDE.md issues the scorer checks the guideline explicitly covers the issue. Default cutoff: "Filter out any issues with a score less than 80." Excluded categories include pre-existing problems, pedantic nitpicks and "General quality concerns not covered by CLAUDE.md". If nothing clears the bar, no review is posted. Threshold editable in `commands/code-review.md`. [code-review README](https://raw.githubusercontent.com/anthropics/claude-code/main/plugins/code-review/README.md)
- The directory listing describes code-review as "5 parallel Sonnet agents"; the plugin's own README says 4. Conflict noted; the README is the more specific source. [plugins dir](https://github.com/anthropics/claude-code/tree/main/plugins); [code-review README](https://raw.githubusercontent.com/anthropics/claude-code/main/plugins/code-review/README.md)
- pr-review-toolkit: `/pr-review-toolkit:review-pr [comments|tests|errors|types|code|simplify|all]` with six named single-purpose agents (comment-analyzer, pr-test-analyzer, silent-failure-hunter, type-design-analyzer, code-reviewer, code-simplifier). [plugins dir](https://github.com/anthropics/claude-code/tree/main/plugins)
- feature-dev: `/feature-dev`, 7-phase workflow with code-explorer, code-architect and code-reviewer agents. [plugins dir](https://github.com/anthropics/claude-code/tree/main/plugins)
- hookify: rules are markdown files at `.claude/hookify.<name>.local.md` with YAML frontmatter (`name`, `enabled`, `event`, `action`, `pattern` or `conditions`) and a message body. Events: `bash`, `file` (Edit, Write, MultiEdit), `stop`, `prompt`, `all`. Actions: `warn` (default, proceeds) or `block` (prevents the tool call, or stops the session on Stop). Conditions use fields such as `file_path`, `new_text`, `user_prompt` with operators `regex_match`, `contains`, `equals`, `not_contains`, `starts_with`, `ends_with`; all conditions must match. Rules apply on next tool use without restart. `/hookify` with no args analyses recent conversation for behaviours the user corrected; `/hookify <instructions>` writes a rule from a description. Requires Python 3.7+, standard library only. [hookify README](https://raw.githubusercontent.com/anthropics/claude-code/main/plugins/hookify/README.md)
- plugin-dev: `/plugin-dev:create-plugin` 8-phase workflow; agents agent-creator, plugin-validator, skill-reviewer. [plugins dir](https://github.com/anthropics/claude-code/tree/main/plugins)
- ralph-wiggum uses a `Stop` hook to intercept exit and keep iterating; security-guidance uses `PreToolUse` to warn on 9 patterns. [plugins dir](https://github.com/anthropics/claude-code/tree/main/plugins)

### Inferences
- code-review's structure maps directly onto a case study section review: two agents check the written rules file (VOICE, portfolio-rules) for compliance, one checks evidence tracing against `reference/`, one checks against the section's decision history; a separate scorer drops anything under 80 or anything not explicitly covered by a written rule. The "not covered by CLAUDE.md" exclusion is the key anti-manufactured-criticism lever and lines up with the user's "never manufacture criticism" rule.
- hookify is the most direct replacement for "write more rules": a `stop` event rule with `action: block` and a condition on a marker file or transcript text could refuse to end a session until a voice pass has been recorded. Caveat: hookify matches text and paths with regex; it cannot judge prose quality. It enforces that a step happened, not that it was done well. The repo already has hand-written hooks (em dash block, evidence file write block), so hookify mostly adds a declarative format and the conversation-mining command; it is not required to get the mechanism.
- `/hookify` with no arguments drafts rules from conversation, which is an AI-written rule. Given the stated distrust of AI-written skills, the safe use is to have it propose and then review each `.local.md` before enabling.
- doc-coauthoring's reader test is the cleanest available fix for "judges its own work": the judge has no drafting context. It suits the "write for the stranger" goal for CS2 (a reader who knows nothing about Mondai).
- Risk: official plugins are Anthropic-maintained, contain no network calls in the cited material except via user-configured connectors. Lowest risk tier in this catalog.

- Last commit date for individual plugin folders inside anthropics/claude-code was not retrieved; only the skills repo date was.
- skill-creator's eval/benchmark mechanics were not retrieved in this pass.

## Community marketplaces and lists: which skills address critique, red teaming, editorial review, fact checking, evaluation, problem framing?

### Takeaway
obra/superpowers is the only community framework with very large adoption whose core is process enforcement (brainstorm before build, plan, verify before claiming done, review between tasks); it is code-centric but its verification-before-completion and requesting-code-review patterns transfer. The big awesome lists are discovery indexes, not vetted sources, and the marketplace ecosystem has a documented malware and prompt-injection problem.

### Cited Findings

### Inferences
- Superpowers' value for a writing repo is not its skills verbatim (they assume tests and git worktrees) but three patterns: a mandatory bootstrap that checks for relevant skills before any task, a "verification before completion" gate and between-task review that blocks on critical issues. The installed `unlazy` covers similar ground (acceptance gates before execution, re-verify evidence before reporting); superpowers is the far more adopted reference implementation of the same idea, so it is the better thing to read and borrow from, not necessarily to install.
- diagnosing-superpowers (transcript review with line-level evidence) is a close match for auditing why a session skipped the voice pass, and worth reading as a pattern.
- Compound Engineering's `/ce-compound` writes learnings to a docs folder as part of the loop, which resembles this repo's LEDGER and DECISIONS practice; the hands-off `/lfg` pushing to remotes is a risk in a portfolio repo and should not be used.
- dlowd/critique has the right mechanism (fresh critic, severity tiers, cross-model triage) but tiny adoption; it is small enough (three files) to read fully, which may make it acceptable under the inspect-before-trust rule. The Codex path adds sandbox and network exposure; the Opus-only default does not.
- Awesome lists should be used only to discover candidates; several have no licence and none vet contents. Given the Snyk numbers, prefer repos that are either in `claude-plugins-official` or small enough to read line by line.

### Gaps
- SkillsMP and claudecodeplugins were not checked directly in this pass; adoption numbers unknown.
- No Hacker News or Reddit complaint threads were retrieved, so failure reports for superpowers (for example skills not triggering after compaction) are only what the README itself admits (Hermes loses the bootstrap after compaction).
- The full wshobson plugin catalog (docs/plugins.md) was not read, so writing or documentation plugins inside it are unconfirmed.
- I found no red-team-for-prose skill with meaningful adoption; red teaming in the ecosystem is code, security or PRD focused (the installed `pm-execution:red-team-prd` is already the closest).

## Eval tooling usable from a repo: which are lightweight enough for one person grading prose?

### Takeaway
promptfoo is the lightest real option: YAML config, `llm-rubric` assertions with a pinned judge model and a numeric threshold, run from the CLI against text. Inspect and OpenAI evals are heavier frameworks built for model benchmarking. For one person grading case study sections, a promptfoo config or the code-review style scorer pattern inside Claude Code is enough.

### Cited Findings
- promptfoo/promptfoo: 25,874 stars, last push 2026-10-10, MIT. [GitHub search API](https://api.github.com/search/repositories?q=repo:promptfoo/promptfoo)
- promptfoo `llm-rubric`: a grader model returns reason, score 0.0 to 1.0 and a pass flag. Without `threshold`, pass is the LLM's boolean; with one, it must pass and meet the score. Judge can be pinned per assertion, test or default (for example `anthropic:claude-sonnet-5` at temperature 0) or via `--grader`. Grades the output it is given, so file text must be fed in as output or a variable; `agent-rubric` exists for judges that need to inspect files. Caveat: "If `pass` is omitted and no threshold is set, any positive score passes." [promptfoo docs](https://www.promptfoo.dev/docs/configuration/expected-outputs/model-graded/llm-rubric/)
- UKGovernmentBEIS/inspect_ai: 2,973 stars, last push 2026-10-10, MIT, "Framework for large language model evaluations". [GitHub search API](https://api.github.com/search/repositories?q=repo:UKGovernmentBEIS/inspect_ai)
- openai/evals: 19,585 stars, last push 2026-04-14 (about six months stale), licence unidentified. [GitHub search API](https://api.github.com/search/repositories?q=repo:openai/evals)
- wshobson `plugin-eval` scores skills with static checks plus experimental LLM-judge and Monte Carlo layers. [README](https://github.com/wshobson/agents)

### Inferences
- A promptfoo setup for prose would be: each test passes one section's text as a variable, with several `llm-rubric` assertions, one per written rule (no em dashes is better as a regex assertion than a judge), each with a threshold. Pinning the judge and temperature 0 gives repeatable grades, and running it is a command, so a session cannot skip it silently if a hook requires its output file.
- Using the same model family as judge and writer still risks shared blind spots; a different-provider grader is possible via promptfoo's provider override, at the cost of another API key.
- Inspect is overkill for one person; openai/evals looks unmaintained in 2026.
- Risk: promptfoo is an npm package that calls model APIs with your key; prompts and draft text leave the machine to the grader provider. Also note promptfoo includes red-teaming and vulnerability scanning features not needed here.

### Gaps
- Braintrust was not researched in this pass (hosted SaaS; data leaves the machine by design).
- No published evidence was found on how well LLM rubric judges agree with a human editor on long-form prose quality.

## Already installed: is there a better alternative?

### Takeaway
For the installed set, the only clear upgrades are patterns rather than replacements: code-review's independent scorer plus threshold (stronger than design-critique or evaluation-rubrics run in the drafting session), doc-coauthoring's context-free reader test and hookify or a hand-written Stop hook to force the voice pass. humanizer and systematic-debugging are already the reference versions.

### Cited Findings
- humanizer installed is blader/humanizer, the most adopted writing skill found (55,426 stars). [GitHub API](https://api.github.com/repos/blader/humanizer)
- systematic-debugging and writing-plans-style skills originate in obra/superpowers (297,186 stars, MIT). [README](https://github.com/obra/superpowers)
- unlazy overlaps superpowers' verification-before-completion and requesting-code-review (gates before execution, re-verify evidence before reporting). [README](https://github.com/obra/superpowers)
- doc-coauthoring is not in the installed list; it is Anthropic-maintained and has no scripts. [SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/doc-coauthoring/SKILL.md)
- hookify is not in the installed list; it is Anthropic-maintained, standard-library Python, declarative rules. [hookify README](https://raw.githubusercontent.com/anthropics/claude-code/main/plugins/hookify/README.md)

### Inferences
- The failures named (skipped voice pass, broken rules, self-judging) are all failures of skills running inside the drafting context. Every effective fix found moves something out of that context: a hook (cannot be skipped), a separate scorer with a cutoff (cannot grade its own draft) or a context-free reader (cannot fill gaps from memory). More skills of the installed kind would not address them.
- evaluation-rubrics and design-critique are useful as rubric sources, but should be run by a separate subagent or promptfoo judge, not by the session that wrote the draft.
- pm-execution:red-team-prd remains the closest red-team tool for prose; nothing better adopted was found.

### Gaps
- The installed copies were not diffed against upstream versions, so whether the local humanizer or systematic-debugging is current was not checked.
- No source was found that measures whether hooks plus external judges actually reduce rule-breaking in writing sessions; that remains untested.
