How you check work you can't read

Your winYou know what you review, where you review it and which mistakes can be undone. You review the site, the same way you would review a build from an engineer. You never have to read code.

Three safety nets

  1. A preview link for every change. I never change the live site directly. Each change goes on its own branch, and Vercel builds that branch at its own web address before it touches chadwickfenner.com. You open the link on your phone and laptop and say yes or no. Nothing reaches the real address until you approve it. ConfirmedThis is your audit. Same skill as design QA on a staging build.
  2. An undo button. GitHub keeps every saved version of the site forever. On the free plan, Vercel can also put the previous live version back in one click if something slips through. ConfirmedMistakes in code, layout or copy are all reversible.
  3. Hidden until launch. The site already tells search engines to stay away: a noindex rule on every page and a robots file that blocks everything. Launch removes both, in five small file changes that are already written down in docs/SITE_SETUP.md.So it can sit on your real domain early, unfinished, with nobody finding it.

On top of that, checks run before you see anything: npm run check fails if any link or image is broken, and browser checks load each page at phone and desktop widths and screenshot them.

What can't be undone

Two things: money once it is spent, and letting the domain lapse. Both are in your hands, not mine, and lesson 2's checklist covers both. Everything else in this process can be put back.

The path from here

  1. Move the domain to Porkbun.You. This week, by 14 Nov. About $12.
  2. Make a Vercel account with your GitHub login and import the portfolio repo. The holding page goes up at a free vercel.app address.You click, I guide. About 10 minutes. $0.
  3. Point chadwickfenner.com at Vercel. Two DNS records at Porkbun. The holding page shows at your real address, still hidden from search.Us together, once the transfer is done. About 15 minutes.
  4. Finish the build: homepage, collection page and case studies. Every change reviewed on its preview link.The work already on the launch tracker.
  5. Site wide QA.Me with the skills above, you audit the result.
  6. Launch. The five file changes go out, search engines are let in.Five minutes of work, reversible like everything else.

Steps 2 and 3 come early on purpose. They prove the whole route from GitHub to your domain works while nothing is at stake, so launch day is a small change instead of a first attempt.
